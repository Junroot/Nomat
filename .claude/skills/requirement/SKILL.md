# 요구사항 분석 & GitHub 이슈 생성

대화 컨텍스트에서 요구사항을 추출하고, 모호한 부분을 명확히 한 뒤, 독립적인 단위로 분리하여 GitHub 이슈를 생성한다.

## 워크플로우

### 1단계: 요구사항 추출

대화 히스토리에서 요구사항 관련 내용을 추출한다:

- 사용자가 명시한 기능, 버그, 개선사항
- 대화 중 합의된 결정사항
- 언급된 제약 조건이나 비기능 요구사항 (성능, 보안 등)
- 암묵적으로 전제된 요구사항 (사용자가 당연하다고 생각하지만 명시하지 않은 것)

추출한 요구사항을 내부적으로 목록화한다. 아직 사용자에게 보여주지 않는다.

### 2단계: 명확화 질문

추출한 요구사항에서 모호하거나 부족한 부분이 있으면 사용자에게 질문한다.
질문이 필요한 상황:

- 구체적인 동작 방식이 불명확할 때 (예: "알림 기능" → 어떤 이벤트에? 어떤 채널로?)
- 경계 조건이 정의되지 않았을 때 (예: 최대 인원수, 타임아웃 시간)
- 에러/예외 상황 처리가 언급되지 않았을 때
- 기존 기능과의 관계가 불분명할 때

질문할 때 `AskUserQuestion` 도구를 활용해 선택지를 제공하면 사용자가 빠르게 답할 수 있다.
모든 질문을 한 번에 모아서 하되, 4개를 초과하면 가장 중요한 것부터 나눠서 질문한다.

명확화가 필요 없을 만큼 충분히 구체적이면 이 단계를 건너뛴다.

### 3단계: 요구사항 분리

하나의 대화에서 나온 요구사항이라도 독립적으로 구현 가능하면 별도 이슈로 분리한다.

**분리 기준:**
- 서로 다른 도메인/모듈에 영향을 주는 요구사항 (예: 백엔드 API 변경 vs 프론트엔드 UI 추가)
- 독립적으로 배포/검증 가능한 단위
- 하나의 이슈가 체크리스트 5개를 초과하면 분리를 검토

**분리하지 않는 경우:**
- 한쪽이 완료되어야 다른 쪽이 의미가 있는 강한 의존관계
- 분리하면 맥락을 잃어 이해하기 어려운 경우

분리 결과를 사용자에게 보여주고, 이슈를 나눌지 합칠지 확인받는다.

### 4단계: 이슈 초안 작성

각 이슈에 대해 아래 템플릿으로 초안을 작성한다.
사용자에게 초안을 제시하고 확인/수정 요청을 받은 후 생성한다.

#### 이슈 본문 템플릿

```markdown
## 배경
[이 요구사항이 필요한 이유와 맥락. 대화에 참여하지 않은 사람도 이해할 수 있도록 작성]

## 요구사항
- [ ] 구체적이고 검증 가능한 항목
- [ ] 각 항목은 하나의 동작을 설명
- [ ] 완료 여부를 명확히 판단할 수 있어야 함

## 수락 기준
- 이 이슈가 "완료"로 간주되기 위한 조건
- 가능하면 "~하면 ~해야 한다" 형식으로 작성

## 참고사항
- 관련 제약 조건, 기술적 고려사항
- 연관 이슈가 있으면 링크
```

#### 라벨 자동 분류

모든 이슈에 `requirement` 라벨을 기본으로 부여하고, 추가로 요구사항 유형에 따라 라벨을 자동 부여한다. 이슈 생성 전 `gh label list`로 저장소에 존재하는 라벨을 확인하고, 없는 라벨은 생성한다.

| 유형 | 라벨 | 판단 기준 |
|------|------|-----------|
| 새 기능 | `feat` | 기존에 없던 기능을 추가 |
| 버그 수정 | `bug` | 기대와 다르게 동작하는 현상 |
| 기존 기능 개선 | `enhancement` | 있는 기능의 동작/UX 변경 |
| 리팩토링 | `refactor` | 동작 변경 없이 코드 구조 개선 |
| 문서화 | `docs` | 문서 추가/수정 |
| 성능 | `performance` | 속도, 메모리, 효율성 개선 |

### 5단계: 이슈 생성

사용자 확인 후 `gh issue create`로 이슈를 생성한다.

```bash
gh issue create --title "이슈 제목" --label "라벨" --body "$(cat <<'EOF'
이슈 본문
EOF
)"
```

- 제목은 한국어로 간결하게 작성한다.
- 여러 이슈를 생성할 때는 순서대로 하나씩 생성하고, 연관 이슈가 있으면 본문에 상호 참조 링크를 추가한다.

### 6단계: 결과 보고

생성된 모든 이슈의 제목과 URL을 목록으로 보여준다.
여러 이슈 간 의존관계나 구현 순서가 있으면 함께 설명한다.

### 7단계: 검증 및 수정 반복

결과 보고 후 자동으로 검증을 수행한다. 검증에 통과할 때까지 아래 과정을 반복한다.

이슈별로 독립된 서브에이전트를 생성하여 검증-수정 루프 전체를 위임한다. 생성된 이슈가 여러 개이면 각 이슈에 대해 **병렬로** 서브에이전트를 실행한다.

```
Agent 도구 호출 (이슈별로 각각):
- description: "이슈 #<번호> 검증 및 수정"
- prompt: |
    이슈 #<번호>에 대해 검증을 수행하고, 실패 시 사용자와 협의하여 수정한 뒤 재검증하는 과정을 통과할 때까지 반복해줘.

    아래 절차를 따라. **최대 3회까지 재검증을 시도**한다.

    1. **검증 실행**: Skill 도구를 사용하여 verify 스킬을 호출한다. args는 '#<이슈번호>'로 전달.

    2. **검증 결과 확인**: 검증 후 이슈에 `verified` 라벨이 추가되었는지 확인한다.
       ```bash
       gh issue view <번호> --json labels --jq '.labels[].name'
       ```
       - `verified` 라벨이 있으면 → 검증 통과. "이슈 #<번호> 검증 통과"를 보고하고 종료.
       - `verified` 라벨이 없으면 → 검증 실패. 3단계로 진행.

    3. **실패 내용 확인 및 사용자 협의**: 최신 검증 코멘트를 조회하여 실패 항목을 파악한다.
       ```bash
       gh api repos/{owner}/{repo}/issues/<번호>/comments --jq '[.[] | select(.body | startswith("## 검증 결과"))] | last | .body'
       ```
       실패 내용을 사용자에게 정리하여 보여주고, AskUserQuestion으로 해결 방안을 물어본다:
       - 검증에서 제안한 방향으로 수정
       - 다른 방식으로 수정 (구체적으로 알려달라고 요청)
       - 해당 항목은 수정하지 않음 (사유 요청)

    4. **이슈 본문 수정**: 사용자의 답변에 따라 이슈 본문을 수정한다.
       ```bash
       gh issue edit <번호> --body "$(cat <<'EOF'
       수정된 이슈 본문
       EOF
       )"
       ```
       수정 후 1단계로 돌아가 재검증을 수행한다.

    5. **재시도 초과**: 3회 시도 후에도 검증을 통과하지 못하면, 남은 실패 항목을 사용자에게 보고하고 AskUserQuestion으로 다음 중 선택하게 한다:
       - 추가 수정 시도
       - 현재 상태로 진행 (verified 라벨 없이)
       - 작업 중단
```

모든 서브에이전트가 완료되면, 각 이슈의 검증 결과 요약을 사용자에게 전달한다.

## 핵심 원칙

- **한국어로 작성**: 이슈 제목, 본문, 라벨 설명 모두 한국어.
- **확인 후 생성**: 이슈 생성 전 반드시 사용자에게 초안을 보여주고 확인받는다. 사용자가 "바로 만들어"라고 하면 확인 단계를 생략할 수 있다.
- **자기 완결적 이슈**: 대화에 참여하지 않은 팀원이 이슈만 보고도 작업할 수 있어야 한다.
- **과도한 분리 금지**: 이슈를 너무 잘게 쪼개면 맥락이 흩어진다. 의미 있는 작업 단위를 유지한다.
