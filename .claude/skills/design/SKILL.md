# 이슈 기반 구현 설계

GitHub 이슈의 요구사항을 분석하고, 코드베이스를 탐색하여 구현에 필요한 설계를 작성한다.
설계 결과는 이슈 코멘트로 남기고, `design` 라벨을 추가한다.

## 워크플로우

### 1단계: 대상 이슈 선정

사용자가 이슈 번호를 명시하면 해당 이슈를 바로 사용한다.

```bash
gh issue view <번호> --json labels --jq '.labels[].name'
```

이슈 번호가 없으면 `requirement` + `verified` 라벨이 모두 붙은 이슈 목록을 보여주고 선택하게 한다.

```bash
gh issue list --label "requirement,verified" --state open
```

목록을 `AskUserQuestion`으로 제시하여 사용자가 선택할 수 있게 한다.

### 1-1단계: 라벨 사전 조건 확인

이슈에 `requirement`와 `verified` 라벨이 **모두** 있는지 확인한다.
조건을 충족하지 않으면 사용자에게 안내하고 **설계를 진행하지 않는다**.

- `requirement` 라벨 없음 → "이 이슈는 요구사항 분석이 완료되지 않았습니다. 먼저 /requirement를 실행해주세요."
- `verified` 라벨 없음 → "이 이슈는 검증이 완료되지 않았습니다. 먼저 /verify를 실행해주세요."

### 2단계: 요구사항 파악

이슈 본문에서 핵심 요구사항을 추출한다:

- 무엇을 구현해야 하는지 (기능/변경사항)
- 수락 기준은 무엇인지
- 제약 조건이나 참고사항

이슈 본문만으로 설계하기에 정보가 부족하면 사용자에게 추가 질문한다.

### 3단계: 코드베이스 분석

요구사항과 관련된 코드를 탐색한다. 이 프로젝트는 헥사고날 아키텍처를 사용하므로, 관련 모듈의 다음 계층을 확인한다:

- **인바운드 어댑터** (`in/`): 컨트롤러, 이벤트 리스너, WebSocket 핸들러 등
- **아웃바운드 어댑터** (`out/`): 저장소 구현체, 외부 서비스 클라이언트
- **도메인** (`application/domain/`): 엔티티, 저장소 인터페이스(포트), 도메인 이벤트
- **서비스** (`application/`): 비즈니스 로직
- **DTO** (`application/dto/`): 요청/응답 객체

프론트엔드가 관련된 경우 라우트(`app/routes.ts`), 컴포넌트, API 호출(`app/utils/api.ts`)도 확인한다.

탐색 시 `Explore` 에이전트나 `Grep`/`Glob` 도구를 활용하여 관련 코드를 효율적으로 찾는다.

### 4단계: 설계 작성

분석 결과를 아래 템플릿으로 정리한다.

#### 설계 코멘트 템플릿

```markdown
## 설계

### 개요
[요구사항을 달성하기 위한 접근 방식을 1-2문장으로 요약]

### 변경 대상

| 파일/클래스 | 변경 유형 | 설명 |
|------------|----------|------|
| `경로/파일명.kt` | 신규/수정/삭제 | 변경 내용 요약 |

### API 설계
(해당하는 경우)

**엔드포인트**: `METHOD /api/v1/...`

요청:
\`\`\`json
{ }
\`\`\`

응답:
\`\`\`json
{ }
\`\`\`

### DB 스키마 변경
(해당하는 경우)

\`\`\`sql
ALTER TABLE ...
\`\`\`

또는 Flyway 마이그레이션 파일에 대한 설명.

### 주요 로직 흐름
[핵심 로직을 단계별로 설명. 복잡한 경우 번호 매기기 사용]

1. 클라이언트가 요청을 보낸다
2. 컨트롤러가 요청을 검증한다
3. 서비스가 비즈니스 로직을 수행한다
4. ...

### 고려사항
- 엣지 케이스, 동시성, 성능 등 구현 시 주의할 점
- 기존 코드와의 호환성
```

해당하지 않는 섹션(예: DB 변경이 없으면 "DB 스키마 변경")은 생략한다.
설계는 구현자가 바로 코딩에 착수할 수 있을 정도로 구체적이어야 한다.

### 5단계: 사용자 확인

설계 초안을 사용자에게 보여주고 확인/수정 요청을 받는다.
사용자가 "바로 올려"라고 하면 확인 단계를 건너뛸 수 있다.

### 6단계: 이슈에 반영

사용자 확인 후 다음을 수행한다:

1. 설계 코멘트 작성:
```bash
gh issue comment <번호> --body "$(cat <<'EOF'
설계 코멘트 내용
EOF
)"
```

2. `design` 라벨 추가 + `verified` 라벨 제거:
```bash
gh issue edit <번호> --add-label "design" --remove-label "verified"
```

라벨이 저장소에 없으면 먼저 생성한다.
`verified` 라벨을 제거하는 이유: 설계가 추가되면 다시 검증(/verify)을 받아야 다음 단계로 진행할 수 있다.

### 7단계: 결과 보고

이슈 URL과 함께 설계가 등록되었음을 알린다.

### 8단계: 검증 및 수정 반복

결과 보고 후 자동으로 검증을 수행한다. 검증에 통과할 때까지 아래 과정을 반복한다.

서브에이전트를 생성하여 검증-수정 루프 전체를 위임한다.

```
Agent 도구 호출:
- description: "이슈 #<번호> 검증 및 수정"
- prompt: |
    이슈 #<번호>에 대해 설계 검증을 수행하고, 실패 시 사용자와 협의하여 수정한 뒤 재검증하는 과정을 통과할 때까지 반복해줘.

    아래 절차를 따라. **최대 3회까지 재검증을 시도**한다.

    1. **검증 실행**: Skill 도구를 사용하여 verify 스킬을 호출한다. args는 '#<이슈번호>'로 전달.

    2. **검증 결과 확인**: 검증 후 이슈에 `verified` 라벨이 추가되었는지 확인한다.
       ```bash
       gh issue view <번호> --json labels --jq '.labels[].name'
       ```
       - `verified` 라벨이 있으면 → 검증 통과. "이슈 #<번호> 검증 통과"를 보고하고 종료.
       - `verified` 라벨이 없으면 → 검증 실패. 3단계로 진행.

    3. **실패 내용 확인 및 사용자 협의**: 최신 검증 코멘트를 조회하여 실패 항목을 파악한다.
       ```bash
       gh api repos/{owner}/{repo}/issues/<번호>/comments --jq '[.[] | select(.body | startswith("## 검증 결과"))] | last | .body'
       ```
       실패 내용을 사용자에게 정리하여 보여주고, AskUserQuestion으로 해결 방안을 물어본다:
       - 검증에서 제안한 방향으로 수정
       - 다른 방식으로 수정 (구체적으로 알려달라고 요청)
       - 해당 항목은 수정하지 않음 (사유 요청)

    4. **설계 코멘트 수정**: 사용자의 답변에 따라 기존 설계 코멘트를 직접 수정한다.
       먼저 `## 설계`로 시작하는 코멘트의 ID를 찾는다:
       ```bash
       gh api repos/{owner}/{repo}/issues/<번호>/comments --jq '.[] | select(.body | startswith("## 설계")) | .id'
       ```
       그 코멘트를 수정한다:
       ```bash
       gh api repos/{owner}/{repo}/issues/comments/<comment_id> -X PATCH -f body="$(cat <<'EOF'
       수정된 설계 코멘트 내용
       EOF
       )"
       ```
       수정 후 1단계로 돌아가 재검증을 수행한다.

    5. **재시도 초과**: 3회 시도 후에도 검증을 통과하지 못하면, 남은 실패 항목을 사용자에게 보고하고 AskUserQuestion으로 다음 중 선택하게 한다:
       - 추가 수정 시도
       - 현재 상태로 진행 (verified 라벨 없이)
       - 작업 중단
```

서브에이전트가 완료되면, 검증 결과 요약을 사용자에게 전달한다.

## 핵심 원칙

- **한국어로 작성**: 설계 코멘트는 한국어로 작성한다.
- **코드 기반 설계**: 추측이 아닌 실제 코드 분석에 기반한다. 관련 코드를 반드시 읽고 설계한다.
- **확인 후 등록**: 이슈 코멘트 작성 전 사용자에게 초안을 보여준다.
- **적정 수준의 상세도**: 구현자가 바로 작업할 수 있을 만큼 구체적이되, 코드를 그대로 작성하는 수준은 아닌 설계를 목표로 한다.
- **기존 패턴 존중**: 코드베이스의 기존 아키텍처 패턴과 컨벤션을 따르는 설계를 한다.
