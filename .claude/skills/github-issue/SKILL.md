# GitHub Issue Creator

GitHub 이슈를 정해진 템플릿에 맞춰 생성한다. 작업 범위가 크면 서브 이슈로 분할한다.

## 이슈 본문 템플릿

```markdown
## 목표

{이슈가 해결되는 기준}

## 배경

{이슈를 생성하게 된 사전 배경}

## 구현 방법

{목표를 달성하기 위한 해결 방법}

## 테스트 방법

{이슈를 해결했는지 여부를 확인하기 위한 방법}
```

## 워크플로우

### 1. 정보 수집

대화 맥락에서 다음 4가지 섹션의 내용을 추론한다:

- **목표**: 이 이슈가 "완료"되려면 무엇이 달성되어야 하는지. 검증 가능한 기준으로 작성한다.
- **배경**: 왜 이 이슈가 필요한지. 현재 상황의 문제점이나 동기를 설명한다.
- **구현 방법**: 목표를 달성하기 위한 구체적인 기술적 접근 방법.
- **테스트 방법**: 구현이 올바르게 되었는지 확인할 수 있는 방법. 수동 테스트 시나리오나 자동화 테스트 등.

대화 맥락만으로 내용이 부족한 섹션이 있다면, 해당 섹션에 대해 사용자에게 질문하여 정보를 수집한다. 모든 섹션이 채워질 때까지 진행하지 않는다.

### 2. 규모 판단 및 서브 이슈 분할

정보가 모이면 구현 방법의 작업 범위를 판단한다.

**서브 이슈로 분할하는 기준**:
- 구현 방법의 항목이 독립적인 작업 단위로 나뉘고, 각각이 별도 PR로 나올 수 있는 규모일 때
- 서로 다른 레이어(인프라 설정, 비즈니스 로직, 이벤트 처리 등)에 걸쳐 있을 때
- 의존 관계가 있어 순차적으로 구현해야 할 때

**분할 방법**:
1. 코드베이스를 탐색하여 현재 상태를 파악한다 (이미 구현된 부분은 제외).
2. 구현 항목을 의존 관계와 레이어 기준으로 그룹화하여 서브 이슈 목록을 만든다.
3. 각 서브 이슈의 제목, 범위, 의존 관계를 표로 정리하여 사용자에게 보여준다.
4. 사용자가 승인하면 서브 이슈를 생성한다.

분할이 불필요한 단순 작업이면 단일 이슈로 바로 진행한다.

### 3. 이슈 미리보기

정보가 충분히 모이면, 이슈 제목과 본문을 작성하여 사용자에게 보여준다. 사용자가 확인하고 수정 요청이 있으면 반영한다.

서브 이슈 분할 시에는 표 형태의 요약만 보여주고, 승인 후 바로 생성한다.

### 4. 이슈 생성

사용자가 승인하면 `gh issue create` 명령어로 이슈를 생성한다:

```bash
gh issue create --title "이슈 제목" --body "$(cat <<'EOF'
## 목표

...

## 배경

...

## 구현 방법

...

## 테스트 방법

...
EOF
)"
```

**서브 이슈 생성 시**:
- 각 서브 이슈 본문 첫 줄에 `> Parent: #N`으로 부모 이슈를 참조한다.
- 배경 섹션에 부모 이슈 번호와 선행 서브 이슈 의존 관계를 명시한다.
- 목표, 구현 방법, 테스트 방법은 해당 서브 이슈의 범위로 한정한다.

생성된 이슈 URL을 사용자에게 전달한다. 서브 이슈가 여러 개이면 의존 관계를 포함한 표로 정리하여 전달한다.

## 작성 가이드라인

- 각 섹션은 간결하되 충분한 정보를 담는다. 한 섹션이 3줄을 넘기면 핵심만 남기고 다듬는다.
- 기술 용어는 팀에서 통용되는 표현을 그대로 사용한다.
- 목표는 "~할 수 있다", "~가 동작한다" 형태의 검증 가능한 문장으로 작성한다.
- 테스트 방법은 구체적인 시나리오(어떤 입력에 어떤 결과가 나와야 하는지)를 포함한다.
