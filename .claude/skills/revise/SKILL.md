# 이슈 수정 & 연쇄 업데이트

워크플로우 각 단계의 이슈를 수정하고, 변경 사항이 하위 단계 이슈에 영향을 주면 함께 수정한다.

## 연쇄 관계

변경이 전파되는 방향:

```
requirement 이슈 본문 → design 코멘트 → task 하위 이슈들
```

- **요구사항 수정**: 설계 코멘트와 task 하위 이슈에 영향을 줄 수 있음
- **설계 수정**: task 하위 이슈에 영향을 줄 수 있음
- **task 수정**: 해당 이슈만 수정 (하위 없음)

## 워크플로우

### 1단계: 대상 이슈 선정

사용자가 이슈 번호를 명시하면 해당 이슈를 바로 사용한다.

```bash
gh issue view <번호> --comments
```

이슈 번호가 없으면 사용자에게 어떤 이슈를 수정할지 물어본다.

### 2단계: 현재 상태 파악

이슈의 라벨과 관계를 파악한다:

- **이슈 본문**: 현재 내용
- **라벨**: `requirement`, `design`, `task`, `verified` 등
- **설계 코멘트**: design 라벨이 있으면 설계 코멘트 확인
- **하위 이슈**: sub-issue 관계가 있는지 확인
- **상위 이슈**: task 이슈라면 상위 이슈 확인

```bash
# 하위 이슈 확인
gh api graphql -f query='
  query {
    repository(owner: "<owner>", name: "<repo>") {
      issue(number: <번호>) {
        subIssues(first: 50) {
          nodes { number title state }
        }
      }
    }
  }
'
```

### 3단계: 수정 내용 확인

사용자가 원하는 수정 내용을 파악한다. 대화 컨텍스트에서 변경사항을 추출하거나, 구체적으로 질문한다:

- 무엇을 변경하고 싶은지
- 변경 이유 (연쇄 수정의 범위를 판단하는 데 도움)

### 4단계: 영향 범위 분석

수정 내용이 하위 단계 이슈에 영향을 주는지 분석한다.

**영향 판단 기준:**
- 요구사항의 수락 기준이 변경되면 → 설계와 task에 영향
- 요구사항에 항목이 추가/삭제되면 → 설계와 task에 영향
- 설계의 변경 대상 파일이 달라지면 → task에 영향
- 설계의 API/DB 스키마가 변경되면 → task에 영향
- 단순 문구 수정, 오타 교정 → 하위에 영향 없음

영향 범위를 사용자에게 보여주고 확인받는다:

```
수정 대상: #123 요구사항 이슈
직접 수정: 이슈 본문의 요구사항 항목 변경
연쇄 수정:
  - #123 설계 코멘트: API 엔드포인트 변경 반영
  - #124 [BE] 방 입장 API: 구현 내용 업데이트
  - #125 [FE] 방 입장 UI: 영향 없음 (변경 불필요)
```

### 5단계: 수정 실행

사용자 확인 후 순서대로 수정한다. 상위부터 하위 순으로 진행한다.

**이슈 본문 수정:**
```bash
gh issue edit <번호> --body "$(cat <<'EOF'
수정된 이슈 본문
EOF
)"
```

**설계 코멘트 수정:**
기존 `## 설계` 코멘트를 찾아 직접 PATCH로 수정한다. 코멘트 본문 내에 변경 이력 섹션을 추가하여 히스토리를 보존한다.

```bash
# 기존 설계 코멘트 ID 조회
COMMENT_ID=$(gh api repos/{owner}/{repo}/issues/<번호>/comments --jq '.[] | select(.body | startswith("## 설계")) | .id')

# 설계 코멘트 직접 수정
gh api repos/{owner}/{repo}/issues/comments/$COMMENT_ID -X PATCH -f body="$(cat <<'EOF'
## 설계

### 변경 이력
- [날짜]: [변경 사항 요약] ([변경 이유])

### 개요
(수정된 설계 내용)

(나머지 설계 섹션)
EOF
)"
```

**task 하위 이슈 수정:**
```bash
gh issue edit <하위이슈번호> --body "$(cat <<'EOF'
수정된 하위 이슈 본문
EOF
)"
```

**verified 라벨 제거:**
수정된 이슈에 `verified` 라벨이 있으면 제거한다. 수정 후 재검증이 필요하기 때문이다.

```bash
gh issue edit <번호> --remove-label "verified"
```

### 6단계: 결과 보고

수정된 모든 이슈의 목록과 변경 내용 요약을 보여준다:

```
수정 완료:
- #123 요구사항: 수락 기준 2개 추가
- #123 설계 코멘트: API 응답 필드 변경 반영
- #124 [BE] 방 입장 API: 구현 체크리스트 업데이트

verified 라벨 제거: #123 (재검증 필요)
```

## 핵심 원칙

- **한국어로 작성**: 모든 수정 내용은 한국어로 작성한다.
- **확인 후 수정**: 영향 범위를 보여주고 사용자 확인 후 수정한다.
- **상위에서 하위로**: 요구사항 → 설계 → task 순서로 수정하여 일관성을 유지한다.
- **변경 이력 보존**: 설계 코멘트는 기존 것을 직접 수정하되, 본문 내 "변경 이력" 섹션에 수정 내역을 기록한다.
- **재검증 유도**: 수정된 이슈의 `verified` 라벨을 제거하여 재검증이 필요함을 표시한다.
- **최소 변경**: 영향받는 부분만 수정한다. 변경과 무관한 내용은 건드리지 않는다.
