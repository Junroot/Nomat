# 이슈 검증

GitHub 이슈의 내용(요구사항, 설계, 구현 계획)을 실제 코드베이스와 대조 검증한다.
문제가 발견되면 수정 방향을 제안하고, 검증 결과를 이슈 코멘트로 남긴다.

## 워크플로우

### 1단계: 대상 이슈 선정

사용자가 이슈 번호를 명시하면 해당 이슈를 바로 사용한다.

```bash
gh issue view <번호> --comments
```

이슈 번호가 없으면 `requirement`, `design`, `task` 라벨이 붙은 열린 이슈 목록을 보여주고 선택하게 한다.

### 2단계: 이슈 단계 파악

이슈의 라벨로 현재 어느 단계까지 진행되었는지 파악하고, 단계에 맞는 검증을 수행한다.

| 라벨 조합 | 단계 | 검증 대상 |
|-----------|------|-----------|
| `requirement` | 요구사항 분석 완료 | 요구사항 자체의 타당성 |
| `requirement` + `design` | 설계 완료 | 설계의 코드베이스 정합성 |
| `requirement` + `design` + `task` 하위 이슈 | 구현 계획 완료 | 계획의 완전성과 실현 가능성 |

### 3단계: 단계별 검증 수행

#### A. 요구사항 검증 (`requirement` 라벨)

이슈 본문의 요구사항을 코드베이스와 대조한다:

- **중복 확인**: 이미 구현된 기능이 아닌지 코드에서 확인
- **의존성 확인**: 요구사항이 전제하는 기존 기능/데이터가 실제로 존재하는지
- **충돌 확인**: 기존 로직과 모순되는 요구사항이 없는지
- **수락 기준 검증 가능성**: 수락 기준이 구체적이고 검증 가능한지

#### B. 설계 검증 (`design` 라벨)

설계 코멘트의 내용을 코드베이스와 대조한다:

- **파일 존재 여부**: 변경 대상으로 명시된 파일/클래스가 실제로 존재하는지
- **아키텍처 정합성**: 헥사고날 아키텍처 컨벤션에 맞는 설계인지 (예: 컨트롤러가 in/, 저장소가 out/ 등)
- **API 설계 일관성**: 기존 API 패턴(URL 구조, 응답 형식)과 일관되는지
- **DB 스키마 호환성**: 기존 마이그레이션 히스토리와 충돌 없는지, Flyway 버전 번호가 겹치지 않는지
- **누락된 변경**: 설계에서 빠진 필수 변경사항이 없는지 (예: DTO 추가 누락, 라우트 등록 누락)

#### C. 구현 계획 검증 (`task` 하위 이슈)

하위 이슈들의 구현 계획을 종합 검증한다:

- **완전성**: 설계의 모든 변경사항이 하위 이슈로 커버되는지
- **의존관계 정확성**: 선행 작업 지정이 올바른지
- **구현 순서 타당성**: 의존관계를 고려한 구현 순서가 맞는지
- **범위 적절성**: 각 하위 이슈의 크기가 적절한지 (너무 크거나 작지 않은지)
- **누락 항목**: 테스트, 마이그레이션, 설정 변경 등 빠진 작업이 없는지

### 4단계: 검증 결과 정리

검증 결과를 아래 형식으로 정리한다.

#### 검증 코멘트 템플릿

```markdown
## 검증 결과

**검증 단계**: 요구사항 / 설계 / 구현 계획
**결과**: ✅ 통과 / ⚠️ 수정 필요 / ❌ 재작업 필요

### 검증 항목

| # | 항목 | 결과 | 비고 |
|---|------|------|------|
| 1 | 파일 존재 여부 | ✅ | 모든 대상 파일 확인됨 |
| 2 | API 일관성 | ⚠️ | 기존 패턴과 URL 구조 불일치 |

### 발견된 문제

#### 문제 1: [제목]
- **내용**: 구체적인 문제 설명
- **영향**: 이 문제가 미치는 영향
- **제안**: 수정 방향

### 결론
[다음 단계로 넘어가도 되는지, 또는 수정 후 재검증이 필요한지]
```

### 5단계: 결과 보고

1. 이슈에 검증 코멘트를 작성한다:
```bash
gh issue comment <번호> --body "$(cat <<'EOF'
검증 코멘트 내용
EOF
)"
```

2. 검증 통과 시 `verified` 라벨을 추가한다:
```bash
gh issue edit <번호> --add-label "verified"
```
라벨이 저장소에 없으면 먼저 생성한다.

3. 사용자에게 요약을 보고한다:
   - 전체 통과 시: 다음 단계로 진행 가능함을 안내
   - 문제 발견 시: 문제점 목록과 수정 제안을 보여주고, 사용자가 어떻게 처리할지 결정하게 한다

## 핵심 원칙

- **코드 기반 검증**: 추측이 아닌 실제 코드를 읽고 대조한다. `Grep`, `Glob`, `Read` 도구를 적극 활용한다.
- **한국어로 작성**: 검증 코멘트는 한국어로 작성한다.
- **구체적 근거**: 문제를 지적할 때 관련 파일 경로와 라인 번호를 함께 제시한다.
- **건설적 제안**: 문제점만 나열하지 않고, 해결 방향을 함께 제시하여 다음 행동이 명확하게 한다.
- **과도한 검증 금지**: 사소한 스타일 차이나 취향 문제는 지적하지 않는다. 실제 구현에 영향을 주는 문제에 집중한다.
