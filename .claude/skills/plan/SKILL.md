# 구현 계획 & 하위 이슈 생성

설계가 완료된 이슈의 요구사항과 설계 코멘트를 읽고, 기능 단위로 구현 작업을 분리하여 하위 이슈로 생성한다.

## 워크플로우

### 1단계: 대상 이슈 선정

사용자가 이슈 번호를 명시하면 해당 이슈를 바로 사용한다.

```bash
gh issue view <번호> --json labels --jq '.labels[].name'
```

이슈 번호가 없으면 `requirement` + `design` + `verified` 라벨이 모두 붙은 이슈 목록을 보여주고 선택하게 한다.

```bash
gh issue list --label "requirement,design,verified" --state open
```

목록을 `AskUserQuestion`으로 제시하여 사용자가 선택할 수 있게 한다.

### 1-1단계: 라벨 사전 조건 확인

이슈에 `requirement`, `design`, `verified` 라벨이 **모두** 있는지 확인한다.
조건을 충족하지 않으면 사용자에게 안내하고 **계획을 진행하지 않는다**.

- `requirement` 라벨 없음 → "이 이슈는 요구사항 분석이 완료되지 않았습니다. 먼저 /requirement를 실행해주세요."
- `design` 라벨 없음 → "이 이슈는 설계가 완료되지 않았습니다. 먼저 /design을 실행해주세요."
- `verified` 라벨 없음 → "이 이슈는 검증이 완료되지 않았습니다. 먼저 /verify를 실행해주세요."

### 2단계: 이슈 분석

선정된 이슈에서 다음을 파악한다:

- **이슈 본문**: 요구사항과 수락 기준
- **설계 코멘트**: 변경 대상 파일, API 설계, DB 스키마, 로직 흐름 등

설계 코멘트가 없으면 사용자에게 알리고, 먼저 `design` 스킬로 설계를 진행할 것을 제안한다.

### 3단계: 구현 작업 분리

설계 내용을 기능 단위로 분리한다. 각 하위 이슈는 독립적으로 구현하고 검증할 수 있어야 한다.

**분리 기준 — 기능 단위:**
- 독립적으로 동작을 검증할 수 있는 단위 (예: "방 입장 API", "방 목록 UI", "DB 마이그레이션")
- 한 사람이 하나의 PR로 완료할 수 있는 크기
- 프론트엔드와 백엔드 변경은 별도 하위 이슈로 분리하되, 함께 동작해야 하면 의존관계를 명시

**분리하지 않는 경우:**
- 단일 파일 수정 수준의 사소한 변경
- 분리하면 의미 없는 단위가 되는 경우 (예: DTO 생성만 따로 분리)

각 하위 이슈에는 구현 순서를 고려하여 번호를 매긴다.

### 4단계: 하위 이슈 초안 작성

각 하위 이슈에 대해 아래 형식으로 초안을 작성한다.

#### 하위 이슈 템플릿

```markdown
## 작업 설명
[이 작업이 무엇인지, 왜 필요한지 1-2문장]

## 구현 내용
- [ ] 구체적인 구현 항목
- [ ] 각 항목은 코드 변경 단위

## 변경 대상 파일
- `경로/파일명` — 변경 설명

## 선행 작업
- 없음 / #이슈번호 (의존하는 하위 이슈)

## 완료 기준
- 어떤 상태가 되면 이 작업이 완료된 것인지
```

### 5단계: 사용자 확인

전체 하위 이슈 초안을 한눈에 볼 수 있도록 요약하여 보여준다:

```
상위 이슈: #123 방 입장 기능 구현

하위 이슈 계획:
1. [DB] 방 참여자 테이블 마이그레이션
2. [BE] 방 입장 API 구현
3. [BE] WebSocket 입장 이벤트 브로드캐스트
4. [FE] 방 입장 UI 구현

의존관계: 2 → 1, 3 → 2
```

사용자가 합치거나 더 나누거나 순서를 변경할 수 있다.
사용자가 "바로 만들어"라고 하면 확인 단계를 건너뛸 수 있다.

### 6단계: 하위 이슈 생성

사용자 확인 후 하위 이슈를 생성한다.

1. 하위 이슈 생성 (구현 순서대로):
```bash
gh issue create --title "[카테고리] 작업 제목" --label "task" --body "$(cat <<'EOF'
하위 이슈 본문
EOF
)"
```

2. 생성된 이슈를 상위 이슈의 하위 이슈로 연결:
```bash
# 생성된 이슈의 node ID 조회
SUB_ISSUE_ID=$(gh issue view <하위이슈번호> --json id -q '.id')

# 상위 이슈에 하위 이슈로 연결
gh api graphql -f query='
  mutation {
    addSubIssue(input: {
      issueId: "<상위이슈_node_id>"
      subIssueId: "'"$SUB_ISSUE_ID"'"
    }) {
      issue { id }
      subIssue { id }
    }
  }
'
```

상위 이슈의 node ID는 `gh issue view <번호> --json id -q '.id'`로 조회한다.

3. 하위 이슈 간 의존관계가 있으면 본문에 "선행 작업: #번호" 형태로 기록한다.

4. `task` 라벨이 저장소에 없으면 먼저 생성한다.

### 7단계: 결과 보고

생성된 하위 이슈 목록을 보여준다:

```
상위 이슈: #123 방 입장 기능 구현

생성된 하위 이슈:
- #124 [DB] 방 참여자 테이블 마이그레이션
- #125 [BE] 방 입장 API 구현 (선행: #124)
- #126 [BE] WebSocket 입장 이벤트 브로드캐스트 (선행: #125)
- #127 [FE] 방 입장 UI 구현
```

### 8단계: 검증 및 수정 반복

결과 보고 후 자동으로 검증을 수행한다. 검증에 통과할 때까지 아래 과정을 반복한다.

하위 이슈(task)별로 독립된 서브에이전트를 생성하여 검증-수정 루프 전체를 위임한다. 여러 하위 이슈가 있으면 **병렬로** 서브에이전트를 실행한다.

```
Agent 도구 호출 (하위 이슈별로 각각):
- description: "이슈 #<하위이슈번호> 검증 및 수정"
- prompt: |
    이슈 #<하위이슈번호>에 대해 구현 계획 검증을 수행하고, 실패 시 사용자와 협의하여 수정한 뒤 재검증하는 과정을 통과할 때까지 반복해줘.

    이 이슈는 상위 이슈 #<상위이슈번호>의 하위 이슈(task)이다.

    아래 절차를 따라. **최대 3회까지 재검증을 시도**한다.

    1. **검증 실행**: Skill 도구를 사용하여 verify 스킬을 호출한다. args는 '#<하위이슈번호>'로 전달.

    2. **검증 결과 확인**: 검증 후 이슈에 `verified` 라벨이 추가되었는지 확인한다.
       ```bash
       gh issue view <하위이슈번호> --json labels --jq '.labels[].name'
       ```
       - `verified` 라벨이 있으면 → 검증 통과. "이슈 #<하위이슈번호> 검증 통과"를 보고하고 종료.
       - `verified` 라벨이 없으면 → 검증 실패. 3단계로 진행.

    3. **실패 내용 확인 및 사용자 협의**: 최신 검증 코멘트를 조회하여 실패 항목을 파악한다.
       ```bash
       gh api repos/{owner}/{repo}/issues/<하위이슈번호>/comments --jq '[.[] | select(.body | startswith("## 검증 결과"))] | last | .body'
       ```
       실패 내용을 사용자에게 정리하여 보여주고, AskUserQuestion으로 해결 방안을 물어본다:
       - 검증에서 제안한 방향으로 수정
       - 다른 방식으로 수정 (구체적으로 알려달라고 요청)
       - 해당 항목은 수정하지 않음 (사유 요청)

    4. **하위 이슈 수정**: 사용자의 답변에 따라 하위 이슈를 수정한다.
       - 본문 수정:
         ```bash
         gh issue edit <하위이슈번호> --body "$(cat <<'EOF'
         수정된 하위 이슈 본문
         EOF
         )"
         ```
       - 하위 이슈 추가가 필요한 경우:
         ```bash
         gh issue create --title "[카테고리] 작업 제목" --label "task" --body "..."
         ```
         생성 후 상위 이슈에 sub-issue로 연결한다.
       - 불필요한 하위 이슈 제거가 필요한 경우:
         ```bash
         gh issue close <번호> --reason "not planned"
         ```
       수정 후 1단계로 돌아가 재검증을 수행한다.

    5. **재시도 초과**: 3회 시도 후에도 검증을 통과하지 못하면, 남은 실패 항목을 사용자에게 보고하고 AskUserQuestion으로 다음 중 선택하게 한다:
       - 추가 수정 시도
       - 현재 상태로 진행 (verified 라벨 없이)
       - 작업 중단
```

모든 서브에이전트가 완료되면, 각 하위 이슈의 검증 결과 요약을 사용자에게 전달한다.

## 핵심 원칙

- **한국어로 작성**: 하위 이슈 제목과 본문은 한국어로 작성한다.
- **설계 기반 계획**: 설계 코멘트를 기반으로 작업을 분리한다. 설계에 없는 작업을 추가해야 할 경우 사용자에게 알린다.
- **확인 후 생성**: 하위 이슈 생성 전 사용자에게 전체 계획을 보여준다.
- **적정 크기 유지**: 하위 이슈 하나가 너무 크면 (체크리스트 7개 이상) 추가 분리를 검토하고, 너무 작으면 (단일 파일 한두 줄 수정) 합치는 것을 제안한다.
- **의존관계 명시**: 작업 간 순서가 중요하면 본문에 선행 작업을 명시하여, 어떤 순서로 구현해야 하는지 파악할 수 있게 한다.
