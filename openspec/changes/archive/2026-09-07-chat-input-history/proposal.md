## Why

방 화면의 채팅 입력창은 게임 중에는 **정답 추측 입력창**이다(`room-round-ui`의 "게임 중 채팅 입력이 정답 추측" 요구사항). 추측은 대개 한 번에 맞지 않는다 — `아이유 좋은날`을 보냈다가 오답이면 `아이유 - 좋은 날`로 고쳐 다시 보내는 식이다. 지금은 오답 뒤 입력창이 비어 있어 **같은 문장을 처음부터 다시 쳐야** 하고, 그 몇 초가 정답 경쟁에서 그대로 손해가 된다.

터미널·IRC·디스코드 등 키보드 중심 입력창은 이 문제를 오래전부터 같은 방식으로 풀어 왔다: **방향키 위/아래로 내가 보낸 것을 다시 불러온다.** 이 change는 그 관례를 채팅 입력창에 그대로 가져온다. 데스크톱에서 `OPEN` 동안 포커스가 이미 입력창에 있으므로(추측을 거기 치므로) 마우스 없이 한 키로 직전 추측을 되살릴 수 있어야 리듬이 끊기지 않는다 — `Shift+Enter` 포기 키를 도입한 것과 같은 이유다.

## What Changes

### front/ — 채팅 입력창의 전송 히스토리 탐색

- `app/utils/InputHistory.ts` **(신규)** — 전송 이력과 탐색 커서를 관리하는 **순수 모델**(React 의존 없음, `ColorSlotAllocator`와 같은 자리·성격). 규칙:
  - 전송 시 이력 끝에 추가. **직전 항목과 같은 내용이면 접는다**(연속 중복 무시 — 셸의 `ignoredups`)
  - 상한 **50개**. 넘치면 가장 오래된 것부터 버린다
  - 위: 커서를 한 칸 과거로. 가장 오래된 항목에서 더 누르면 그대로
  - 아래: 커서를 한 칸 현재로. 이력 끝을 지나면 **탐색을 시작하기 전에 치고 있던 미전송 텍스트(draft)를 복원**한다
  - 탐색을 시작하는 첫 위 키에서 그 시점의 입력값을 draft로 보관한다
  - 탐색 중 타이핑하면 탐색이 끝나고, 편집된 텍스트가 새 draft가 된다(bash처럼 이력 항목을 제자리에서 고치지 않는다)
  - 전송하면 커서가 이력 끝으로 돌아가고 draft는 비워진다
- `app/components/ui/ChatInput.tsx` — `onKeyDown`에 `ArrowUp`/`ArrowDown` 분기를 추가하고 `InputHistory`를 `useRef`로 들어 연결한다. 히스토리는 **이 컴포넌트가 소유**한다 — 입력값 상태가 여기 있고, 부모(`RoomView`)를 다시 렌더시키지 않기 위해서다. 서버가 에코한 `messages`(남의 메시지가 섞이고 피드 상한으로 앞이 잘림)에서 파생하지 않는다
- 키 처리 규칙:
  - **IME 조합 중에는 발화하지 않는다**(`isComposing` 가드). `Enter`·`Shift+Enter`와 같은 판정을 쓴다. 한글 조합 중 방향키에 이력을 갈아끼우면 조합 중이던 글자가 깨진다
  - 브라우저 기본 동작(단일 행 `<input>`에서 위/아래 = 캐럿을 맨 앞/뒤로)을 막고, 불러온 텍스트의 **캐럿은 끝에** 둔다(셸과 동일)
- 생존 범위는 **방 세션 동안만**이다. `ChatInput`이 언마운트되면(방 퇴장·화면 이탈) 이력도 사라진다. `sessionStorage`/`localStorage`에 저장하지 않는다
- 모바일에는 방향키가 없으므로 자연히 데스크톱 전용이 된다. 별도 UI 힌트·버튼은 두지 않는다

### back/ · infra/ — 변경 없음

프론트 전용 변경이다. 채팅 전송 계약(`/app/rooms/chat`)·서버 이벤트·DB·ES·Kafka·Redis 영향 없음.

## Capabilities

### New Capabilities

- `chat-input-history`: 채팅 입력창에서 방향키 위/아래로 자신이 보낸 메시지를 시간 역순으로 불러오는 동작. 이력의 소유 범위(내가 보낸 것만, 방 세션 동안만), 연속 중복 접기와 상한, draft 보존·복원, 탐색 중 편집 시의 탈출, IME 조합 중 비발화, 캐럿 위치를 규정한다.

### Modified Capabilities

- 없음. `room-round-ui`의 채팅 입력·포기 키 요구사항은 그대로이며, 이 change는 그 위에 독립된 입력 편의 기능을 얹는다.

## Impact

- **서브프로젝트**: `front/`만. `back/`·`infra/` 영향 없음
- **도메인 모듈**: 백엔드 모듈 변경 없음. 대응 화면은 `room` 도메인의 방 화면이다
- **헥사고날 계층**: 해당 없음(프론트 전용)
- **DB 스키마 / ES 매핑 / Kafka 토픽 / Redis 키**: 영향 없음
- **API 계약 변화**: 없음
- **외부 의존성**: 신규 npm 패키지 없음
- **영향 받는 화면**: `/rooms/:roomId`의 채팅 입력창. 방 상태(`ACTIVE`/`PLAYING`)와 라운드 단계(`OPEN`/`REVEAL`)에 무관하게 동일하게 동작한다
- **파일**:
  - 신규 — `app/utils/InputHistory.ts`
  - 수정 — `app/components/ui/ChatInput.tsx`(키 분기 + 모델 연결)
  - 손대지 않음 — `RoomView.tsx`, `useRoomSubscription.ts`, `ChatMessageList.tsx`. 전송 경로와 피드는 그대로다
- **동작 변화**:
  - 데스크톱에서 입력창 포커스 상태로 `↑`를 누르면 마지막으로 보낸 메시지가 입력창에 채워진다 **(주 기능)**
  - `Enter`·`Shift+Enter`·전역 Enter 포커스 이동·전송 버튼 활성 조건은 변하지 않는다
  - 방향키를 쓰지 않는 사용자에게는 아무 변화가 없다
- **검증 제약**: 프론트에 테스트 프레임워크가 없으므로 자동 검증은 `npm run typecheck`·`npm run build`에 그친다. 순수 모델을 분리한 것은 나중에 테스트를 붙일 때의 진입점을 남기기 위해서이기도 하다. 키 동작(특히 IME 조합·캐럿 위치)은 브라우저에서 수동 확인한다
