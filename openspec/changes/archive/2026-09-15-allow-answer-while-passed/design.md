## Context

`RoundService.submitAnswer()`는 정답 판정 전에 포기 여부를 한 번 읽고, 포기 중이면 아무 일도 하지 않고 반환한다.

```
포기 상태인 참가자가 정답을 침
        │
        ▼
┌───────────────────────────────────┐
│ RoomStompController.chat()        │
├───────────────────────────────────┤
│ ① Redis publish → 채팅 방송  ✅    │ ← 원문이 모두에게 보인다
│ ② roundService.submitAnswer()     │
└───────────────┬───────────────────┘
                ▼
        phase == OPEN ?
                │ yes
                ▼
     isPassing(me) ── yes ──▶ return        ⬅ 지우려는 게이트
                │ no                          (전이 X · 점수 X · 피드백 X)
                ▼
     AnswerMatcher.matches → tryAdvanceOnCorrect → REVEAL
```

게이트는 **서버에만 있다.** 프론트는 `passed` 불리언으로 토글 상태만 그리고, 입력창은 포기 여부와 무관하게 동작한다. 그래서 무시당한 참가자에게 전달되는 신호가 0이다. 게다가 ①이 ②보다 먼저이므로, 무시된 정답은 **다른 사람에게는 이미 보인 뒤다.**

원래 설계(`2026-09-03-add-round-pass-signal` Decision 4)는 이 게이트를 "포기의 대가"로 의도했다. 대가가 없으면 시작하자마자 눌러 놓고 계속 추측하는 것이 지배 전략이 되어 매 라운드가 조기 종료된다는 논리였다.

문제는 **대가를 지불하는 방식이 참가자에게 보이지 않는다**는 데 있다. 보이지 않는 대가는 억제가 아니라 함정이다. 억제로 기능하려면 누르기 *전에* 알아야 하는데, 이 대가는 누른 *뒤에* 정답이 씹히는 형태로만 드러난다. 그마저도 "내가 포기해서 씹혔다"로 해석되지 않는다 — 아무 설명이 없으므로.

## Goals / Non-Goals

**Goals**

- 포기 상태에서 친 정답이 다른 참가자의 정답과 **완전히 동일하게** 판정된다
- 그로 인해 침묵 실패와 정답 유출이 함께 사라진다
- 포기의 나머지 계약(토글·라운드 경계 해제·2/3 임계·인원수 전파·퇴장 재평가)은 **한 글자도 바뀌지 않는다**
- 되돌릴 수 있게 남긴다 — 왜 뒤집었는지, 어떤 조건에서 다시 억제가 필요한지를 문서로 못 박는다

**Non-Goals**

- 포기 가능 시점 제한(클립 1회 재생 전 비활성화 등) — 이 change에서 넣지 않는다 (Decision 2)
- 점수 감점형 대가 — 채택하지 않는다 (Alternatives)
- 프론트 변경 — 없다. 고칠 UI가 없다
- 포기 임계 비율(2/3) 조정 — 이 change의 범위 밖이다

## Decisions

### Decision 1 — 포기는 "이 라운드 넘기자"는 **투표**이며 채점과 직교한다 (Decision 4 반전)

`submitAnswer()`에서 `isPassing` 게이트를 제거한다. 포기 상태는 오직 임계 판정(`passed × 3 >= remaining × 2`)에만 쓰이고, 정답 자격에는 관여하지 않는다.

**근거**: 두 모델의 비용을 실제 관측으로 다시 달았다.

| | 현재(대가 모델) | 채택(투표 모델) |
|---|---|---|
| 포기 후 떠오른 정답 | 씹힘 — 피드백 없음 | 정상 인정 |
| 무시된 정답의 운명 | 이미 방송돼 남이 가로챔 | 즉시 전이돼 가로챌 틈 없음 |
| "모르겠어요"의 체감 | 위험한 버튼 | 부담 없는 버튼 |
| 조기 종료 억제 | 있음(보이지 않는 형태) | 없음(임계·사회적 압력만) |

왼쪽 세 줄은 **관측된 것**이고, 오른쪽 아래 한 줄은 **가정된 것**이다. 확인된 피해를 가정된 남용보다 우선한다.

덧붙여, 이 게임은 친구끼리 하는 방 단위 놀이지 승점을 다투는 랭크전이 아니다. 포기 인원수가 실시간으로 모두에게 보이고 임계가 2/3로 높다는 점까지 더하면, 원래 우려했던 "전원이 조직적으로 남용"은 성립하기 어렵다.

### Decision 2 — 억제 장치를 **대체하지 않고 비운다**

Decision 1로 조기 종료 억제 축이 하나 사라지는데, 이 change는 그 자리를 다른 것으로 메우지 않는다.

**근거**: 지금 억제를 넣으면 **어느 설계가 효과가 있었는지 영영 알 수 없다.** 대가를 빼면서 동시에 시점 제한을 넣으면, 이후 조기 종료가 없어도 그것이 "애초에 우려가 기우였기 때문"인지 "시점 제한이 막아줬기 때문"인지 구분되지 않는다. 한 번에 하나씩 바꾼다.

**언제 다시 넣나 — 판정 기준을 미리 적어 둔다.** 아래 중 하나가 관측되면 별도 change로 **포기 가능 시점 제한**을 검토한다.

- 한 게임에서 포기 임계로 끝난 라운드가 절반을 넘는 상태가 반복된다
- 클립이 한 번도 다 돌기 전에 끝나는 라운드가 흔해진다
- "곡이 나오다 말고 끊긴다"는 불만이 실제로 제기된다

그때의 조치는 **채점이 아니라 타이밍** 축이다 — 클립 1회 재생 완료 전(또는 `OPEN` 지속의 일정 비율 경과 전)에는 포기 컨트롤을 비활성화한다. 조기 종료의 최악(3초 만에 끊김)만 막고 채점은 건드리지 않는다. 이 축은 Decision 1과 독립이므로 이 change를 되돌리지 않고 얹을 수 있다.

**되돌리기(대가 모델 복원)는 최후 수단이다.** 그것을 택하려면 침묵 실패와 정답 유출을 UI로 먼저 해결해야 한다 — 포기 상태에서 입력창을 잠그거나 "포기 중에는 정답 판정에서 제외됩니다"를 누르기 전에 보여주는 식으로. 보이지 않는 대가로 되돌아가는 것은 어떤 경우에도 채택하지 않는다.

### Decision 3 — `isPassing` 포트를 남기지 않고 제거한다

`RoundStateStore.isPassing`, `RoundStateStoreImpl.isPassing`, `IS_PASSING_SCRIPT`를 모두 지운다.

**근거**: 유일한 호출자가 사라진다. 헥사고날 포트는 **애플리케이션이 실제로 요구하는 것**의 목록이어야 하고, 아무도 부르지 않는 메서드가 인터페이스에 남아 있으면 다음 사람이 "정답 판정이 포기를 본다"고 읽는다 — 정확히 이 change가 없애려는 오해다.

**잃는 것과 대체**: `IS_PASSING_SCRIPT`는 lazy reset 계약(`passSeq == roundSeq`일 때만 포기 집합이 유효)을 **원자적으로** 읽는 유일한 경로였다. 그 원자성은 판정 도중 라운드가 전이돼 결과가 뒤집히는 것을 막기 위한 것이었는데, 판정 자체가 사라지므로 요구도 함께 사라진다.

lazy reset 계약 자체는 여전히 살아 있고(`snapshot`·`togglePass`·`onPlayerLeft`·`START_SCRIPT`가 모두 지킨다), **회귀 테스트도 계속 필요하다.** `isPassing`으로 이 성질을 검증하던 테스트는 지우지 않고 `snapshot(roomId, viewerId).passing`으로 옮긴다 — 같은 판별식을 쓰는 읽기 경로다. 원자성은 잃지만 그 테스트가 보려던 것은 원자성이 아니라 **판별식의 정확성**이었다.

### Decision 4 — 포기자가 스스로 맞혀도 포기 표를 명시적으로 해제하지 않는다

포기 상태인 참가자가 정답을 맞히면 `tryAdvanceOnCorrect`가 `OPEN → REVEAL` 전이를 수행한다. 이때 `passes` Set에서 그 참가자를 빼는 처리를 **추가하지 않는다**.

**근거**: 필요가 없다. 라운드가 전이된 시점에서 그 라운드의 포기 집합은 의미를 잃고, 다음 `OPEN`에서 `passSeq != roundSeq`로 무효화된다(lazy reset). 굳이 지우면 Redis 왕복이 하나 늘고, 전이 CAS와 Set 삭제 사이의 경합이라는 **없던 문제**가 생긴다.

표시상으로도 문제없다 — 전이와 동시에 `ROUND_REVEALED`가 나가고 프론트는 `ROUND_STARTED`에서 포기 표시를 0으로 초기화한다. "내가 넘기자고 투표해놓고 내가 맞혔다"가 잠깐 성립하지만, 이는 모순이 아니라 "듣다 보니 생각났다"의 정상적인 서사다.

### Decision 5 — 스펙은 "지우고 끝"이 아니라 "지우고 명시"한다

제거한 요구사항 자리에 **`포기는 정답 판정에 영향을 주지 않는다`**를 새로 넣는다.

**근거**: 요구사항을 빼기만 하면 스펙은 이 질문에 **침묵**한다. 침묵한 스펙은 다음 사람에게 "정해지지 않은 것"으로 읽히고, "포기자가 정답 맞히는 거 좀 이상한데?" 한마디에 되돌아간다. 명시적으로 뒤집은 결정은 명시적으로 기록한다 — 근거(침묵 실패·정답 유출)와 함께.

### Decision 6 — 낡은 방송 시나리오 정정을 이 change에 포함한다

`라운드는 첫 정답 또는 클립 소진으로 종료된다`의 시나리오 `- **AND** 정답 채팅 원문은 일반 채팅으로 방송되지 않아야 한다`를 현재 동작에 맞게 고친다.

**근거**: 코드는 정답 여부와 무관하게 항상 방송한다 — `RoomStompController.chat()`이 판정보다 **먼저** Redis로 publish하고, 주석도 그렇게 적혀 있다. 이 시나리오는 이 change와 무관하게 이미 틀렸다.

그럼에도 여기에 포함하는 이유는 범위 확장이 아니라 그 반대다. 제거 대상 요구사항의 다음 문장이 현재 스펙에서 **정답 원문 방송을 올바르게 서술하는 유일한 곳**이다.

> 이는 정답과 일치하는 채팅에도 예외 없이 적용된다 — 라운드가 `OPEN`인 채로 원문이 방송되어 다른 참가자가 그것을 보고 답할 수 있다는 점은 **의도적으로 수용한 동작**이며 …

이것만 빼면 스펙에는 틀린 문장만 남는다. 이 change가 스펙을 **더 부정확하게** 만들지 않으려면 같이 고쳐야 한다. 코드 변경은 0이고 문장 하나를 사실에 맞춘다.

## 사라지는 코드 경로

```
RoundStateStore (포트)
  └─ isPassing(roomId, playerId): Boolean          ← 삭제

RoundStateStoreImpl (어댑터)
  ├─ override fun isPassing(...)                   ← 삭제
  └─ IS_PASSING_SCRIPT (Lua)                       ← 삭제
        EXISTS round → HGET passSeq == roundSeq → SISMEMBER passes

RoundService
  └─ submitAnswer()
        if (roundStateStore.isPassing(...)) return  ← 삭제 (KDoc 문단 교체)
```

남는 것: `round:{roomId}:passes` Set, `passSeq` 해시 필드, `togglePass`·`onPlayerLeft`·`START_SCRIPT`의 lazy reset, `snapshot`의 `passedCount`·`passing`. **포기 기능 자체는 그대로다.**

## 데이터 영향

- **Redis 키**: 추가·삭제·스키마 변경 없음. TTL 정책 변경 없음
- **DB / ES / Kafka**: 영향 없음
- **Redis Pub/Sub 채널**: `room:{roomId}:events` 그대로. `RoundPassUpdatedEventMessage`·`RoomEventMessage` 스키마 변경 없음
- **전파 메시지 빈도**: 변화 없음. 포기 토글 시에만 현황이 나가는 것은 동일하다

## Risks / Trade-offs

| 위험 | 평가 |
|---|---|
| "일단 누르고 계속 추측"이 지배 전략이 된다 | Decision 1·2가 정면으로 받는다. 억제를 비우고, 판정 기준과 다음 조치(시점 제한)를 미리 적어 두었다 |
| 조기 종료가 늘어 "곡이 나오다 말고 끊긴다"로 바뀐다 | 위와 같은 축. 관측되면 Decision 2의 기준에 따라 별도 change |
| 배포 중 구·신 인스턴스 혼재로 같은 방에서 판정이 갈린다 | 라운드 단위로 끝나고 영속 상태가 남지 않는다. 두 동작 모두 게임을 깨지 않으므로 플래그 없이 롤링 배포 |
| lazy reset 회귀가 테스트 밖으로 새어 나간다 | Decision 3대로 검증을 `snapshot(...).passing`으로 옮겨 유지한다. 커버리지를 줄이지 않는다 |
| 포기자가 정답을 맞히는 것이 이상하게 읽힌다 | Decision 4. 모순이 아니라 "듣다 보니 생각났다"이며, 전이와 함께 표가 자연 소멸한다 |
| 정답 유출이 남는다 | 오히려 줄어든다. 정답이 즉시 라운드를 끝내므로 남이 보고 따라 칠 창이 닫힌다 |

## 롤아웃 / 롤백

- 피처 플래그 없음. 롤링 배포
- 롤백은 `git revert` 하나. Redis 키 구조를 건드리지 않으므로 되돌려도 진행 중인 방이 깨지지 않는다
- 관측 포인트: 포기 임계로 끝난 라운드의 비율, 라운드 평균 지속 시간. Decision 2의 판정 기준이 이 둘을 본다
