## Context

정답 판정 규칙은 `AnswerMatcher`에 있다.

```kotlin
private fun normalize(value: String): String = value.filterNot { it.isWhitespace() }.lowercase()
```

공백 제거 + 소문자화가 전부다. 이 규칙은 한국어 제목에서는 그럭저럭 동작하지만, **표기 체계가 여럿인 언어에서 무너진다.** 일본어는 같은 발음을 히라가나·가타카나·전각·반각으로 쓸 수 있고, 작은 가나 표기도 흔들린다.

관련해서 `fix-additional-title-collation`이 저장 계층의 동치 기준을 코드포인트 일치로 못 박았다. 이제 관용도 스펙트럼은 이렇게 된다.

```
   엄격 ◀──────────────────────────────────────────────────▶ 관용

   코드포인트 일치            ★ 본 변경이 놓을 지점 ★        utf8mb4_unicode_ci
   ├ DB (0900_bin)            NFKC + 대소문자                (더 이상 쓰지 않음)
   └ AnswerMatcher (현재)     + 가나 접기 + 비문자 제거       탁점까지 접음
        │                            │
        └──── 앱이 여기서 ──────────▶│
                                      DB 는 왼쪽 끝에 고정 — 판단하지 않는다
```

**판단은 애플리케이션 한 곳에서만 한다.** 저장소는 글자가 다르면 다르다고만 말하고, 무엇이 같은 정답인지는 `TitleNormalizer`가 정한다.

## 선행 change 와의 역할 분담 — 계층이 아니라 "접는 축의 집합"으로 갈린다

두 change 는 같은 capability(`playlist-track-answer`)에 요구사항을 넣는다. 서로 뒤집지 않는 이유를 명시해 둔다.

- **선행 change**: 저장소가 **판단하지 않게** 만든다. 표기가 다르면 저장을 거부하지 않는다.
- **본 change**: 애플리케이션이 **무엇을 같다고 볼지** 정한다.

"계층이 다르니 충돌하지 않는다"는 설명만으로는 부족하다. 선행 요구사항이 *"이 값들은 함께 저장될 수 있어야 한다"*처럼 **API 로 관측되는 결과**를 약속하면, 본 change 가 그중 가나 축을 접는 순간 그 문장은 거짓이 된다. 그래서 선행 change 의 요구사항을 **저장 계층 보증**("저장소의 비교 규칙이 저장 거부의 원인이 되지 않는다")으로 재진술하고, 가나 시나리오와 그 조합을 검증하던 테스트(선행 `tasks.md` 2.2)를 함께 제거했다.

진짜 경계는 **접는 축의 집합**이다.

```
   utf8mb4_unicode_ci 가 접는 축          TitleNormalizer 가 접는 축
   ┌────────────────────────────┐
   │  히라가나 ↔ 가타카나        │◀────┐
   │  큰 가나 ↔ 작은 가나        │◀──┐ │  ⊃ (진부분집합)
   │  전각 ↔ 반각                │◀┐ │ │
   │  대소문자                   │◀┼─┼─┤
   │ ─────────────────────────── │ │ │ │
   │  탁점·반탁점   ★차집합★     │ (접지 않음)
   └────────────────────────────┘
```

차집합은 **탁점**이다. 그래서 선행 change 의 저장 계층 보증은 본 change 이후에도 실제로 필요하다 — 정규화는 탁점을 접지 않으므로 `ハハ`/`ババ` 는 여전히 두 값으로 저장되어야 하는데, `unicode_ci` 는 그 둘을 동일시해 PK 충돌을 일으킨다. 정규화가 콜레이션 수정을 대체하지 못하는 것도, 두 delta 가 `## ADDED Requirements` 로 공존할 수 있는 것도 같은 이유다.

## Goals / Non-Goals

**Goals**

- 같은 곡을 가리키는 표기 흔들림을 정답으로 인정한다
- 사용자가 표기 변형을 추가 정답으로 일일이 등록하지 않아도 되게 한다
- 규칙을 "무엇을 접고 무엇을 접지 않는가"의 **원칙**으로 세워, 이후 판단의 기준이 되게 한다

**Non-Goals**

- 오타 허용·유사도 매칭(편집 거리 등) — 표기 정규화와 다른 문제다. 게임성에 미치는 영향이 커서 별도 논의가 필요하다
- 로마자 ↔ 가나 상호 변환 (`maiwei` = `マイウェイ`) — 발음 변환이지 표기 정규화가 아니다
- 장음 규칙화 (`メイド` = `メード`) — 규칙으로 못 박기 어렵고 오답을 정답 처리할 위험이 있다
- ES 검색(`playlist-search-sync`)의 분석기 — 플레이리스트 제목 검색은 별개 경로이고 Nori가 담당한다

## Decision 1: "표기는 접고 정보는 보존한다"

**결정**: 정규화가 버려도 되는 것은 **표기 방식**이고, 버려서는 안 되는 것은 **내용**이다.

| 축 | 예 | 판정 | 근거 |
|---|---|---|---|
| 전각 ↔ 반각 | `ﾏｲｳｪｲ` / `マイウェイ` | **접음** | 입력기 차이일 뿐 |
| 히라가나 ↔ 가타카나 | `まいうぇい` / `マイウェイ` | **접음** | 표기 흔들림의 전형 |
| 작은 가나 ↔ 큰 가나 | `ウェイ` / `ウエイ` | **접음** | 장애를 일으킨 바로 그 축 |
| 대소문자 | `Monster` / `monster` | **접음** | 기존 규칙 유지 |
| 공백·구두점·기호 | `밤을 달리다!` / `밤을달리다` | **접음** | 정보를 담지 않는다 |
| 탁점·반탁점 | `ハハ` / `ババ` | **접지 않음** | `かっこう`(뻐꾸기) ≠ `がっこう`(학교). 접으면 오답을 정답 처리 |
| 장음 부호 | `メール` / `メル` | **접지 않음** | 발음이 다르다 |
| 괄호 안의 내용 | `Monster` / `Monster (feat. X)` | **접지 않음** | 괄호 안은 정보다 |

마지막 줄이 중요하다. `(feat. …)`·`(Remix)` 같은 꼬리표를 통째로 지우면 매칭은 너그러워지지만 **정보를 버리는 것**이라 원칙에 어긋난다. 사용자가 `Monster`만으로도 맞히게 하고 싶다면 그것을 추가 정답으로 등록하면 된다 — 그것이 추가 정답의 용도다.

괄호 **문자** 자체(`(`, `)`, `【`, `「`)는 구두점이므로 Decision 2의 규칙에 따라 제거된다. 내용은 남는다.

## Decision 2: 규칙을 카테고리로 정의한다 — `[^\p{L}\p{N}]`

**결정**: 공백·구두점·기호를 개별 열거하지 않고 "문자(`\p{L}`)와 숫자(`\p{N}`)가 아닌 것"을 모두 제거한다.

```
   개별 열거                       카테고리 규칙
   ─────────────                   ─────────────
   공백 제거          ┐
   구두점 제거        ├──▶         [^\p{L}\p{N}] 제거
   기호 제거          │
   괄호 문자 제거     ┘
```

이 정의가 일본어에서 정확히 원하는 대로 갈라진다는 점이 채택 근거다.

| 문자 | 코드포인트 | 카테고리 | 처리 | 결과 |
|---|---|---|---|---|
| `・` 중점 | U+30FB | Po | 제거 | `マイ・ウェイ` = `マイウェイ` |
| `〜` 물결 | U+301C | Pd | 제거 | `夏〜Summer〜` = `夏Summer` |
| `ー` 장음 | U+30FC | **Lm (문자)** | 보존 | `メール` ≠ `メル` |
| `々` 반복 | U+3005 | **Lm (문자)** | 보존 | `人々` 유지 |

장음 부호를 지켜야 한다는 요구가 **규칙에 예외를 쓰지 않고** 충족된다. Unicode 카테고리가 이미 "발음에 기여하는 문자"와 "장식"을 갈라 놓았기 때문이다.

`\p{L}`/`\p{N}`은 Java 정규식에서 기본 지원되고, JS에서는 `u` 플래그로 지원된다. 이중 구현의 표면적을 줄여준다.

## Decision 3: 정규화는 비교에만 쓰고 저장은 원문 그대로 한다

**결정**: 읽기 시점 정규화. `additional_title`에는 사용자가 입력한 문자열을 그대로 저장한다.

| | 쓰기 시점 정규화 | **읽기 시점 정규화** ✅ |
|---|---|---|
| 저장값 | 정규화 키 | 사용자 입력 원문 |
| 비교 비용 | 0 | 비교마다 정규화 |
| 편집 화면 표시 | 가타카나로 뭉개져 보임 ✗ | 입력 그대로 ✓ |
| 규칙 변경 | 재마이그레이션 필요 | 즉시 반영 ✓ |

`PlaylistWithTrackResponse`가 추가 정답을 그대로 편집 화면에 내려주므로 원문 보존이 필수다. 히라가나로 입력한 값을 가타카나로 바꿔 돌려주면 사용자는 자기가 입력한 것을 잃는다.

**비용**: `RoundService.submitAnswer`가 채팅 1건마다 `track.additionalTitles + track.title`을 정규화한다. 최대 11개의 짧은 문자열이고, 같은 메서드가 이미 채팅마다 `roomPlaylistTrackRepository.findByRoomId`로 DB를 조회하고 있어 상대적으로 미미하다. 라운드 시작 시 정규화 결과를 캐시하는 최적화는 필요해지면 그때 한다.

## Decision 4: 매칭과 중복 판정에 같은 규칙 하나를 쓴다

정규화가 관용적일수록 부작용이 하나 따라온다.

```
   관용도 ↑
      ├─ 매칭이 너그러워짐          (의도한 것)
      └─ 중복 제거도 공격적이 됨    (의도치 않은 것)
```

그래서 노브를 둘로 나누는 안 — 중복 판정은 보수적으로, 매칭만 관용적으로 — 을 검토했다. **기각한다.**

```
   두 추가 정답 A, B 가 매칭 규칙상 구분 불가하다
        ▼
   플레이어가 무엇을 입력하든 A와 B는 항상 같은 판정을 낸다
        ▼
   B를 추가로 저장해서 얻는 것이 없다 (순수 노이즈)
        ▼
   ∴ 매칭 규칙과 중복 판정 규칙은 같아야 정합적이다
```

`マイウェイ`를 등록한 뒤 `マイ・ウェイ`가 차단되어도 손해가 없다 — 관용 매칭이 이미 그 입력을 정답으로 인정한다. 규칙이 하나면 구현·테스트 부담도 절반이다.

**대가는 UX다.** 사용자 눈에 두 값은 명백히 다른 글자다. 그래서 프론트의 안내 문구는 "중복입니다"(차단)가 아니라 **"이미 등록된 정답으로 인정됩니다"**(이미 커버됨)로 읽혀야 한다. Decision 1이 괄호 내용을 보존하기로 한 덕분에 차단 사례는 순수한 표기 흔들림으로 한정되어, 납득 가능한 범위에 머문다.

## Decision 5: 정규화 결과가 비면 두 단계로 폴백한다

`[^\p{L}\p{N}]` 제거는 문자·숫자가 하나도 없는 제목을 빈 문자열로 만든다 — 밴드명 `!!!`, 제목 `★` 같은 실재하는 사례다.

**결정**: 결과가 비면 **공백만 제거한 값**으로 폴백한다. 제거를 통째로 건너뛰지 않는다.

```
   "!!!"  vs  "! ! !"
      통째 건너뛰기 → "!!!" ≠ "! ! !"    ✗ 표기 흔들림이 살아남음
      공백만 제거   → "!!!" = "!!!"      ✓

   그리고 "공백만 제거"는 현행 AnswerMatcher 의 규칙 그 자체 →
   문자·숫자 없는 제목의 판정이 배포 전후로 바뀌지 않는다 (회귀 방지)
```

폴백이 현행 규칙과 정확히 연속되므로, `★` 하나짜리 정답은 지금도 배포 후에도 `★`로 매칭된다.

## Decision 6: 서버는 거부하지 않고 조용히 접는다

프론트가 사전 차단하더라도 공개 API이므로 서버 백스톱이 필요하다. 400을 던지지 않고 조용히 중복을 접는다.

```
   레거시 플레이리스트에 "マイ ウェイ" 와 "マイウェイ" 가 이미 저장돼 있다
   (fix-additional-title-collation 이전의 ci 는 공백을 접지 않아 저장 가능했다)
        │
        ▼  사용자가 그 플레이리스트를 열어 곡 하나만 고치고 저장
        │
        ├─ 서버가 400 → 저장 불가. 사용자는 이유를 모른 채 편집이 막힌다 ✗
        └─ 서버가 조용히 접음 → 저장 성공, 노이즈가 정리된다 ✓
```

프론트는 **새로 추가하는 항목**만 막을 수 있고 이미 목록에 있는 항목은 막지 못한다. 서버가 거부하면 레거시 데이터를 가진 플레이리스트가 편집 불가 상태로 잠긴다.

## Decision 8: 추가 정답 요청 필드는 `Set`이 아니라 `List`다

**구현 중 발견**. Decision 6이 "먼저 등록된 값을 남기고 이후 중복을 버린다"고 정했는데,
`PlaylistCreationRequestTrack.additionalTitles`가 `Set<String>`이면 이 규칙이 **성립하지 않는다.**

```
   요청 JSON  ["マイ・ウェイ", "マイウェイ"]
        │
        ▼  Jackson 이 Set<String> → java.util.HashSet 로 역직렬화
        │
   DTO 도달 시  [マイウェイ, マイ・ウェイ]   ← 입력 순서가 이미 사라졌다
        │
        ▼  "먼저 온 값" 이 무엇인지 알 수 없다
```

**결정**: 요청 필드 타입을 `List<String>`으로 바꾼다.

- **JSON 계약은 그대로다** — 양쪽 다 JSON 배열이고, 프론트는 이미 `string[]`을 보낸다.
  순서는 클라이언트가 원래 가지고 있던 정보이고 서버 타입이 그것을 버리고 있었을 뿐이다.
- `toDomain()`이 정규화 키로 접으면서 `Set`으로 좁힌다. 저장 계층(`Track.additionalTitles`)은
  `@ElementCollection Set<String>` 그대로 — 저장 순서는 어차피 무의미하다.
- **부수효과**: `@field:Size(max = 10)`이 접기 **전** 원본 개수를 센다. 종전에는 `Set` 역직렬화가
  완전히 같은 문자열을 미리 접어줬으므로, 같은 값 11개를 보내는 병적인 요청은 통과하다 이제 400이
  된다. 예산 검사가 느슨해지는 게 아니라 엄격해지는 방향이라 허용한다.

## Decision 7: 규칙은 `common/`에 두고, 프론트는 같은 규칙을 재구현한다

**배치**: `AnswerMatcher`는 `room/application/domain`에 있고 중복 판정은 `playlist` 모듈이 필요로 한다. 모듈 간 도메인 직접 참조는 헥사고날 경계를 흐리므로, 순수 규칙을 `common/`(이미 `exception`·`metadata`·`lock`이 사는 곳)에 둔다. 기술적 횡단 관심사가 아니라 **도메인 규칙**이므로 `infrastructure/`가 아니다.

**프론트 재구현의 리스크**: 규칙이 Kotlin과 TypeScript 양쪽에 살게 된다.

```
   titleNormalizer.ts        TitleNormalizer.kt
          │      두 구현이 갈라지면      │
          ▼                              ▼
   프론트가 통과시킨 입력을 서버가 조용히 접거나, 프론트가 과하게 차단
```

완화 요소: NFKC는 양쪽 다 표준 내장(`java.text.Normalizer` / `String.prototype.normalize`)이고, 나머지는 코드포인트 산술과 12글자 매핑 테이블이라 각각 10줄 안팎이다. 갈라져도 결과는 "차단이 어긋나는" 정도이고 데이터 무결성은 `fix-additional-title-collation`의 PK가 지킨다.

**미해결 리스크**: JDK와 JS 엔진의 Unicode 버전 차이로 NFKC 결과가 미세하게 갈릴 수 있다. 가나·구두점 범위에서는 안정적이라 실용상 문제없다고 보지만, 완전히 배제하지는 못한다.

## 구현 순서 의존

파이프라인의 두 가나 단계는 **순서가 규칙의 일부**다.

```
   NFKC  →  히라가나→가타카나  →  작은 가나→큰 가나
              ↑                      ↑
              ぁ → ァ                ァ → ア
              (히라가나 작은 글자도 이 순서라야 최종 ア 로 수렴)
```

히라가나→가타카나를 먼저 해야 작은 가나 매핑 테이블을 가타카나 12자로만 유지할 수 있다. 순서를 바꾸면 히라가나 작은 글자를 위한 테이블이 하나 더 필요해진다.
