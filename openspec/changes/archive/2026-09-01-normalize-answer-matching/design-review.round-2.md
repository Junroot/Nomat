# design.md 적대적 리뷰

검증 통과한 `[치명]`·`[높음]` 지적 없음.

설계가 코드에 대해 하는 주장(현행 `AnswerMatcher.normalize`, `RoundService.submitAnswer` 의 채팅당 조회 경로, `Track` 상수, `PlaylistWithTrackResponse` 의 원문 반환, `common/` 의 기존 구성, 프론트 `AdditionalTitleEditor.tsx:26` 결함)을 모두 실제 파일에서 확인했고 전부 일치했다. 정규화 파이프라인이 Decision 1·2 의 축별 표대로 갈리는지도 JDK 17 과 Node 18 에서 직접 실행해 확인했으며, 표의 8개 축 판정이 양쪽 런타임에서 동일하게 재현됐다.

## 기각한 후보

적대적으로 세웠다가 근거가 서지 않아 버린 의심들이다. 판정 신뢰를 위해 근거와 함께 남긴다.

**선행 change 요구사항과의 잔여 모순** — `fix-additional-title-collation` 의 요구사항 제목("추가 정답의 유일성은 **문자 단위 일치**로 판정한다")과 첫 SHALL 이 남아 있어, 본 change 의 "표기 정규화 후 같은 값이 되는 두 항목을 함께 보관하지 않아야(SHALL NOT)" 와 같은 capability 안에서 충돌하는지 의심했다. 반증: 그 요구사항 본문이 "이것은 **저장 계층의 보증**이다. 무엇을 같은 정답으로 볼지는 애플리케이션이 정하고, 저장소는 그 판단에 개입하지 않는다… 이 축들의 두 값이 최종적으로 함께 남는지는 애플리케이션의 정규화 규칙이 정하며, **이 요구사항은 그것을 약속하지 않는다**" 로 판단 권한을 명시적으로 애플리케이션에 넘긴다. 가나 시나리오도 실제로 삭제되어 있고(`fix-additional-title-collation/specs/playlist-track-answer/spec.md` 전문, 시나리오 4개 모두 탁점·완전동일값·수정경로), 선행 `tasks.md` 의 가나 조합 태스크도 제거된 뒤 2.1~2.4 가 전부 탁점 조합이다. `design.md:33` 의 "재진술하고 … 테스트를 함께 제거했다" 는 실제 문서 상태와 일치한다.

**"관용도가 넓어지는 방향으로만 바뀐다" 는 단정의 반례** (`proposal.md` Impact 마지막 줄) — 현행 규칙에서 정답이던 입력이 새 규칙에서 오답이 되는 조합을 찾으려 했다. 반증: 새 규칙은 NFKC 후 `[^\p{L}\p{N}]` 을 전부 제거하므로 공백 제거는 그 부분집합이고, 대소문자 접기도 유지된다. JDK 17·Node 18 실행으로 기존 `AnswerMatcherTest` 의 전 케이스(`밤을 달 리다`·`밤을\t달리다`·`Hello World`/`helloworld`·`alt title`/`ALT TITLE`)가 여전히 일치함을 확인했다. 유일하게 세운 반례는 "결합 탁점(U+3099)과 기반 문자 사이에 공백이 끼어 NFKC 합성이 차단되는 문자열"인데, 실제 입력으로 성립하지 않아 폐기했다.

**플레이리스트 수정 경로의 중복 접기 누락** — 설계가 중복 접기를 `PlaylistCreationRequest` 한 곳에만 두어, 수정 경로(spec 시나리오 "레거시 중복이 있는 플레이리스트도 수정할 수 있다")가 비어 있는지 의심했다. 반증: `PlaylistService.kt:29,44` 와 `PlaylistController.kt:33,42` 에서 저장·수정이 **동일한 `PlaylistCreationRequest`** 를 받고, `playlist/application/dto/` 에 별도 Update DTO 가 없다. 한 곳 수정으로 두 경로가 모두 덮인다.

**부수 효과 전파 경로 누락(ES 색인·Kafka·방 스냅샷)** — 중복 접기로 저장 값이 달라지는데 설계가 "ES 매핑·Kafka 토픽 영향 없음" 이라고 단정하는 근거를 의심했다. 반증: `PlaylistDocument.kt:13-20` 의 색인 필드는 `title`·`description`·`id` 뿐이라 `additionalTitles` 는 ES 에 실리지 않는다. 방 스냅샷(`RoomService.kt:95-108`)은 저장된 값을 그대로 복사할 뿐 판정을 하지 않으므로, 레거시 중복이 복사되어도 매칭 결과가 달라지지 않는다.

**`\p{L}`/`\p{N}` 의 런타임 지원 주장** (`design.md:109`) — Java 정규식에서 한 글자 일반 카테고리가 기본 동작하지 않아 규칙이 통째로 깨질 가능성을 의심했다. 반증: JDK 17.0.19 에서 `replaceAll("[^\\p{L}\\p{N}]","")` 이 `ー`(Lm)·`々`(Lm) 보존, `・`(Po)·`〜`(Pd) 제거로 설계 표대로 동작했다. Node 18 의 `/[^\p{L}\p{N}]/gu` 결과도 12개 케이스 전부 JDK 와 일치해, Decision 7 이 "미해결 리스크" 로 이미 수용한 Unicode 버전 차이가 이 규칙 범위에서는 현재 관측되지 않는다.

판정: 진입 가능 — 설계의 코드 주장이 실제 코드와 모두 일치하고, 정규화 규칙의 축별 판정이 JDK·JS 양쪽에서 설계 표대로 재현되며, 선행 change 와의 요구사항 충돌은 문서 상태로 확인한 결과 실제로 해소되어 있다.
