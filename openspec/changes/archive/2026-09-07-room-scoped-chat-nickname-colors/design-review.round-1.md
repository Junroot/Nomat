# design.md 리뷰 — room-scoped-chat-nickname-colors (라운드 1)

검토 범위: `design.md`, `proposal.md`, `tasks.md`, `specs/room-chat-nickname-color/spec.md`. 코드 검증은 `design-review-verified.md`에 기록했다.

슬롯 배정(Decision 1~3)의 코드 주장은 전부 실제 코드와 일치했다. 살아남은 지적은 팔레트(Decision 5) 한 건이다.

### [높음] Decision 5의 hex 표가 설계가 밝힌 생성 파라미터·간격 주장과 다르고, 스펙의 "앞 8개 45° 이상"은 18° 격자에서 애초에 불가능하다

- **위치**: `design.md` Decision 5 (L 0.74 / C 0.16, 18° 간격, 시작 211.5°, 거리순 탐욕 배치, "슬롯 0~7 서로 45° 이상 / 8·9는 22.5°", "배경 대비 전부 10:1 이상"), `design.md` Risks "[11명 이상…] 앞 10명까지는 22.5° 이상", `specs/room-chat-nickname-color/spec.md` 요구사항 "배정 순서가 앞설수록…" (SHALL: 앞 8개 45° 이상, 앞 10개 22.5° 이상) 및 시나리오 "평균 인원의 방은 뚜렷한 색만 쓴다", `tasks.md` 1.1(표 그대로 추가 + 파라미터 주석) · 6.5
- **설계 주장**: 표의 20색은 OKLCH L 0.74·C 0.16 고정, 색상환 18° 등분(211.5° 시작), 거리순 탐욕 배치의 결과이며, 슬롯 0~7은 서로 45° 이상, 슬롯 0~9는 22.5° 이상 떨어져 있고, 배경 대비는 전부 10:1 이상이다. 스펙은 이 수치를 SHALL 요구사항으로 굳혔다.
- **무엇이 깨지나**:
  1. **표가 파라미터와 맞지 않는다.** 표의 hex를 OKLCH로 되돌리면 L은 0.760~0.831로 흩어져 있고(0.74인 슬롯 없음), 색상은 211.5°+18k 격자에 놓여 있지 않다(슬롯 0이 192.4°, 211.5°인 슬롯 없음; 234.5→253.5→281.4→312.8→343.4처럼 파랑·보라 구간 간격이 19~31°로 불균등 — "채도만 깎았다"면 색상은 보존돼야 한다). 배치도 탐욕 거리순이 아니다: 슬롯 0~3 배정 후 가장 먼 미배정 색은 343.4°(거리 58.9°)인데 슬롯 4는 그보다 가까운 74.3°(슬롯 1과 32.1°)다. 즉 표를 "그대로 추가하고 파라미터를 주석으로 남기는" tasks 1.1은 **재현되지 않는 파라미터**를 주석으로 남기게 된다.
  2. **간격 주장이 표에서 성립하지 않는다.** 슬롯 0~7의 최소 쌍 색상차는 27.8°(슬롯 0 `#00ddd9` 청록 vs 슬롯 6 `#59daff`하늘)이고, 슬롯 1–4(32.1°, 살구 vs 주황), 슬롯 2–5(30.5°, 연두 vs 초록)도 45° 미만이다. 슬롯 0~9의 최소는 15.5°(슬롯 1–9, `#ff9469` vs `#f99743`)로 22.5° 미만이자 격자 간격 18°보다도 좁다. 결과적으로 Goals의 "평균 인원 방에서는 항상 구분이 확실한 색만 쓰인다"가 7명 방에서 이미 깨지고(비슷한 쌍 3개), 스펙 시나리오 "8명 이하 → 서로 45° 이상"은 표대로 구현하면 **검증 시 실패**한다.
  3. **스펙 요구가 수학적으로 불가능하다.** 18° 격자 20점에서 8점을 고르면 간격(격자 단위) 합이 20이므로 최소 간격은 2칸=36° 이하다(3칸씩이면 24>20). 따라서 "앞 8개 45° 이상"은 팔레트를 파라미터대로 다시 생성해도 만족할 수 없고, "22.5°"도 격자의 배수가 아니라 실제 값은 18° 또는 36°다. SHALL로 적힌 수치가 팔레트 정의 자체와 모순되므로, 표를 고치든 수치를 고치든 **설계 단계에서 결정**해야 한다(구현자가 국소적으로 못 정한다: 스펙 계약이자 팔레트라는 되돌리기 비싼 선택).
  4. 부수: "대비 전부 10:1 이상"도 사실이 아니다(최소 8.97:1, 8개 슬롯이 10:1 미만). 스펙 기준 7:1은 전 슬롯이 만족하므로 이 항목만으로는 지적이 아니나, 같은 표의 사실 오류라 함께 정정할 대상이다.
- **검증 근거**: `design-review-verified.md`의 hex 표 OKLCH 환산 항목(변환기는 `#ff0000→(0.628, 0.2577, 29.23°)`, `#0000ff→(0.452, 0.3132, 264.05°)` 표준값으로 검증, `#22d3ee`→211.53°로 설계의 시작점 서술과 일치함을 확인) — 슬롯별 L·H 목록, 슬롯 0~7 최소 27.8°, 슬롯 0~9 최소 15.5°, 대비 최소 8.97:1. 스펙 인용: `spec.md` "앞 8개 슬롯은 서로 45° 이상, 앞 10개는 22.5° 이상 떨어져 있어야(SHALL)". 설계 인용: `design.md` "슬롯 0~7 … 서로 45° 이상 … 8·9 … 22.5°", "배경 `#0a0a0f` 대비는 전부 10:1 이상이다".

## 기각한 후보

- **`SESSION_REPLACED`가 실제로는 `LEFT`/`JOINED`를 동반해 슬롯이 풀리거나 재배정되지 않는가** — 반증. `RoomJoinChannelInterceptor.kt:45-63`에서 같은 방 세션 교체는 `cancelPendingLeave`만 호출하고 `join`/`leave`를 타지 않으므로 `SESSION_REPLACED`만 방송된다. 다른 방으로의 교체는 옛 방에 `LEFT`가 가는데, 그건 진짜 퇴장이라 설계의 해제 규칙과 일치한다.
- **유예 중 재접속 시 `JOINED`가 다시 와 슬롯이 바뀌지 않는가** — 반증. 활성 세션 없는 CONNECT에서 `cancelPendingLeave`가 true면 `join`을 호출하지 않아 `RoomJoinedEvent`가 없고(`RoomJoinChannelInterceptor.kt:65-67`, `Room.kt:83-96`), 어차피 `assign`은 멱등이라 중복 `JOINED`가 와도 슬롯은 유지된다.
- **StrictMode 이펙트 재실행으로 배정 Map이 초기화되거나 방 상세가 두 번 배정되지 않는가** — 반증. ref는 재실행에도 유지되고, `useRoomSubscription.ts:245-262`는 `subscriptionRef.current`가 있으면 구독·`fetchRoomDetail`을 건너뛰며, cleanup의 100ms 지연 정리는 재실행 시 `clearPendingTimeout()`으로 취소된다.
- **`appendMessage` 외에 메시지를 만드는 경로가 있어 `colorSlot`이 빠진 메시지가 생기지 않는가** — 반증. 파일 내 `setMessages` 호출은 `appendMessage`(:114-120) 하나뿐이고, 색이 필요한 `type: "message"` 생성은 `CHAT` 분기(:169) 한 곳이다.
- **Tailwind v4에서 `@theme` 변수가 미사용이면 안 나온다는 주장이 설치 버전에 맞지 않는가** — 반증 불가/설계 유리. 설치 버전 4.0.9의 `dist/lib.js`에 `static` 테마 옵션이 존재하므로 "기본은 사용분만, `@theme static`으로 전량"이라는 설계 서술과 정합한다. 어느 쪽이든 리터럴 클래스 배열 방식은 동작한다.

판정: 조건부(치명·높음 1건 선해결) — Decision 5의 팔레트 표를 밝힌 파라미터로 실제 재생성해 표·간격 주장·대비 주장을 일치시키고, 스펙의 "앞 8개 45° 이상 / 앞 10개 22.5° 이상"을 18° 격자에서 달성 가능한 수치(예: 앞 8개 36° 이상, 앞 10개 36° 이상 또는 실제 측정값)로 고치거나 팔레트 생성 규칙을 바꿔 두 문서가 서로·실제 색과 맞도록 결정한 뒤 진입한다.
