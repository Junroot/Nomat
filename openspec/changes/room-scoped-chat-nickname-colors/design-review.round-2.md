# design-review — room-scoped-chat-nickname-colors (라운드 2)

검토 범위: `design.md`, `proposal.md`, `tasks.md`, `specs/room-chat-nickname-color/spec.md`. 코드 주장은 `design-review-verified.md` 캐시(라운드 1)와 이번 라운드에 직접 연 파일로 검증했다. 라운드 1에서 지적된 팔레트 표는 재생성된 표(`design.md:120-131`)를 OKLab 변환기로 다시 계산해 확인했다.

살아남은 지적은 1건이다.

### [높음] 스펙 SHALL "슬롯 0~9 서로 36° 이상"을 설계의 hex 표 자체가 만족하지 못한다 (실측 최소 35.74°)

- **위치**: `specs/room-chat-nickname-color/spec.md:322` (SHALL) 및 `:326-328` (시나리오 "36° 이상"), `design.md:41` (Goals), `design.md:112,116` (Decision 5 "결과: 슬롯 0~9는 서로 36° 이상"), `design.md:133` ("최소 색상 간격은 35.7°"), `proposal.md:176`, `tasks.md:219` (hex 표를 "그대로" 추가)
- **설계 주장**: 스펙은 "앞 10개 슬롯(0~9)은 서로 36° 이상 떨어져 있어야(SHALL) 한다"고 못 박고, 시나리오도 "표시된 색들이 서로 색상환에서 36° 이상 떨어진 색이어야 한다"를 검증 조건으로 둔다. 설계 Goals·Decision 5 본문·다이어그램·proposal 도 같은 "36° 이상"을 쓴다.
- **무엇이 깨지나**: 같은 Decision 5 가 한 줄 아래에서 "슬롯 0~9의 최소 색상 간격은 35.7°"라고 스스로 적고 있고, 실측도 그렇다 — 슬롯 3 `#aaaaff`(283.2°)와 슬롯 7 `#70bbff`(247.5°)의 색상차는 **35.74°** 다. 격자는 36° 간격이지만 hex 로 양자화하면서 ±0.5° 오차가 붙어, 표를 그대로 옮기는 순간(tasks 1.1) 스펙 SHALL 과 시나리오 "36° 이상"이 **결정적으로** 불만족이 된다. 이 스펙은 archive 시 main spec 이 되므로 출시 팔레트가 영구히 위반하는 SHALL 을 남기게 되고, `openspec-verify-change` 도 같은 조건으로 실패한다. 기능 결함은 아니고 문서 계약의 수치 오류이나, 스펙 요구사항 자체이므로 설계 시점에 정정해야 한다. 수정은 기계적이다: SHALL 과 설계 본문·다이어그램·proposal 의 "36° 이상"을 "격자 기준 36° (sRGB 양자화 오차 ±0.5°, 실측 최소 35.7°)" 처럼 실측이 만족하는 서술로 바꾸거나, 임계값을 35° 로 낮춘다(둘 중 하나로 통일). 슬롯 10~19 의 "이웃과 18°"(실측 최소 17.2°) 도 같은 방식으로 함께 맞춘다.
- **검증 근거**: `design-review-verified.md` 라운드 2 항목 — hex 표 OKLab 변환 실측 색상(슬롯 3: 283.2°, 슬롯 7: 247.5°), 슬롯 0~9 최소 쌍 색상차 35.74°(슬롯 3–7), 전체 최소 17.22°(슬롯 3–17). 변환기는 `#ff0000`→H 29.23°, `#0000ff`→H 264.05° 로 표준값과 일치함을 확인. `design.md:133` 의 자체 수치(35.7°)와도 일치.

## 기각한 후보

- **hex 표가 생성 규칙·표의 수치와 다르다는 의심(라운드 1 재발 여부)** — 반증. 재생성 표 20개 전부 L 0.769~0.771, 표의 색상(°)과 실측 차이 ≤0.48°, 채도·대비 열 실측 일치, 대비 최소 8.85:1(슬롯 9)로 전부 7:1 초과. "짝수 격자점 먼저 거리순 탐욕, 동률은 작은 색상" 규칙을 손으로 재현하면 31.5→211.5→103.5→283.5→67.5→139.5→175.5→247.5→319.5→355.5, 홀수점은 전부 18° 동률이라 오름차순 — 표의 슬롯 순서와 정확히 같다. (캐시 라운드 2 항목)
- **뷰어의 STOMP 재연결 중 놓친 `LEFT` 로 슬롯이 누수돼 만석 방에서 폴백 충돌이 난다는 의심** — 반증. `front/app/utils/stomp.ts:12-19` 는 `reconnectDelay: 0` 이고 `useRoomSubscription.ts`·`RoomConnectionStore.ts` 에 재연결·재구독 로직이 없다. 연결이 끊기면 그 훅 세션은 끝나고 재입장은 새 훅 인스턴스(새 Map)다. 설계의 "훅 인스턴스 = 방 세션" 전제가 코드와 맞는다.
- **컴포넌트가 유지된 채 `roomId` 만 바뀌면 이전 방의 Map 이 새 방으로 넘어온다는 의심** — 반증. `useRoomSubscription.ts:240-243` 에서 `storeRoomId !== roomId` 면 즉시 `navigate("/")` 라 방 화면이 언마운트되고, 새 방 입장은 새 client·새 훅으로만 가능하다.
- **`CHAT` 이 방 상세보다 먼저 와 색이 비거나 나중에 뒤집힌다는 의심** — 설계가 Decision 2 의 `CHAT` 경로와 tasks 3.2/3.4 로 명시적으로 다루며, `assign` 이 기존 슬롯을 우선하므로 상세 도착이 색을 바꾸지 않는다. 코드상 구독→`fetchRoomDetail` 순서(`useRoomSubscription.ts:245-262`)와 일치.
- **`LEFT` 뒤에 같은 발신자의 `CHAT` 이 도착해 떠난 사람이 슬롯을 점유(누수)한다는 의심** — `RoomStompController.kt:61-77` 의 chat 은 멤버십 검사 없이 세션 속성만으로 발행하므로 자발 퇴장 직후 RTT 창에서 이론상 가능하나, 클라이언트가 `LEFT` 수신 즉시 연결을 끊고(`useRoomSubscription.ts:155-165`) 서버 세션 속성도 인터셉터가 관리하므로 재현 창이 밀리초 단위이고, 누수 결과도 만석(20명) 방에서만 폴백에 닿는다. `[높음]` 으로 세울 재현 시나리오를 만들지 못해 폐기.

판정: 조건부(치명·높음 1건 선해결) — 스펙 SHALL·설계 본문·proposal 의 "슬롯 0~9 서로 36° 이상"(및 "이웃과 18°")을 hex 표 실측(최소 35.7°/17.2°)이 만족하는 서술로 통일한 뒤 진입.
