# login-redirect Specification

## Purpose

로그인이 필요한 요청이 실패했을 때 **사용자를 로그인 화면으로 보내고, 로그인 후 원래 있던 자리로 정확히 한 번 돌려보내는** 흐름을 정의한다. 핵심은 "미인증(401)"과 "권한·정책 위반(403)"을 서버가 서로 다른 상태 코드로 구분하고, 프론트가 401에서만 화면을 이동시키는 것이다. 401 응답은 본문·`WWW-Authenticate` 헤더·리다이렉트 없이 상태 코드만 돌려주어 브라우저 기본 인증 대화상자나 CORS 차단을 유발하지 않으며, 403은 한국어 거부 사유를 JSON 본문으로 담아 그 자리에서 토스트로 보여줄 수 있게 한다. 로그인 화면으로의 이동은 여러 요청이 동시에 401을 받아도 정확히 한 번만 일어나고, 언제나 현재 전체 주소를 인코딩한 복귀 주소(`redirectUrl`)를 함께 전달한다. 로그인 화면은 복귀 주소가 없으면 메인(`/`)으로, 외부 origin이면 이동하지 않고 잘못된 진입 경로 화면으로 처리한다. 내 정보(`me`) 적재는 렌더 부수효과가 아니라 전역 스토어의 책임이며, 중복 요청은 진행 중인 요청을 재사용해 합쳐진다.

## Requirements

### Requirement: 서버는 미인증과 권한 없음을 서로 다른 상태 코드로 구분한다

시스템(백엔드)은 **인증되지 않은 주체가 보호된 리소스를 요청하면 `401 Unauthorized`로 응답해야(SHALL)** 하고, **인증된 주체가 권한·정책 위반으로 거부될 때는 `403 Forbidden`으로 응답해야(SHALL)** 한다.

401 응답은 본문 없이 상태 코드만 반환해야(SHALL) 하며, **`WWW-Authenticate` 헤더를 포함하지 않아야(SHALL NOT)** 한다 — 브라우저의 기본 인증 대화상자가 뜨지 않아야 한다. 401 응답은 **리다이렉트(3xx)여서는 안 된다(SHALL NOT)** — 인가 서버(Discord)로 302를 보내면 브라우저가 이를 따라가 CORS로 차단되고, 클라이언트가 상태 코드를 읽을 수 없게 된다.

403 응답은 거부 사유를 담은 한국어 메시지를 JSON 본문(`{ "message": ... }`)으로 포함해야(SHALL) 한다.

이 구분은 **운영 설정과 테스트 설정에서 동일해야(SHALL)** 한다.

#### Scenario: 인증 쿠키 없이 보호된 엔드포인트를 호출하면 401이다
- **WHEN** 인증 쿠키 없이 `GET /players/me`를 호출함
- **THEN** 응답 상태는 `401`이어야 한다
- **AND** 응답에 `WWW-Authenticate` 헤더가 없어야 한다
- **AND** 응답이 리다이렉트가 아니어야 한다

#### Scenario: 만료되거나 위조된 토큰도 401이다
- **WHEN** 유효하지 않은 값이 담긴 인증 쿠키로 `GET /rooms`를 호출함
- **THEN** 응답 상태는 `401`이어야 한다

#### Scenario: 로그인한 사용자가 남의 리소스를 수정하면 403이다
- **WHEN** 플레이어 A가 플레이어 B의 플레이리스트에 대해 `PUT /playlists/{id}`를 호출함
- **THEN** 응답 상태는 `403`이어야 한다
- **AND** 응답 본문의 `message`에 거부 사유가 담겨야 한다

#### Scenario: 로그인한 사용자가 상한을 초과하면 403이다
- **WHEN** 플레이리스트를 상한만큼 보유한 플레이어가 `POST /playlists`를 호출함
- **THEN** 응답 상태는 `403`이어야 한다
- **AND** 응답 본문의 `message`에 상한 안내가 담겨야 한다

#### Scenario: 인증이 필요 없는 경로는 영향을 받지 않는다
- **WHEN** 인증 쿠키 없이 `/html/**`, `/login/**`, actuator 엔드포인트를 호출함
- **THEN** 401이 아니라 기존과 동일한 응답이 반환되어야 한다

### Requirement: 클라이언트는 미인증 실패에서만, 정확히 한 번 로그인 화면으로 이동한다

시스템(프론트)은 API 응답이 **`401`일 때만 로그인 화면으로 이동해야(SHALL)** 한다. `403`을 받은 요청은 **화면을 이동시키지 않고(SHALL NOT)** 실패를 호출부로 전파해야(SHALL) 한다.

여러 요청이 동시에 401을 받더라도 **이동은 정확히 한 번만 일어나야(SHALL)** 한다. 이동이 시작된 뒤 도착한 401은 아무 일도 하지 않아야(SHALL) 한다.

이동 시 **현재 화면의 전체 주소를 복귀 주소로 항상 함께 전달해야(SHALL)** 하며, 주소는 쿼리 파라미터 값으로 안전하게 인코딩되어야(SHALL) 한다 — `&`·`?` 등이 포함되어도 잘리지 않아야 한다.

#### Scenario: 로그아웃 상태로 메인에 들어가면 복귀 주소와 함께 로그인 화면으로 간다
- **WHEN** 인증 쿠키 없이 `/`에 진입하여 방 목록과 내 정보 요청이 모두 401을 받음
- **THEN** `/login?redirectUrl=<인코딩된 원래 주소>`로 이동해야 한다
- **AND** 복귀 주소 없는 `/login`으로 이동해서는 안 된다

#### Scenario: 여러 요청이 동시에 401을 받아도 이동은 한 번이다
- **WHEN** 한 화면에서 세 개의 요청이 거의 동시에 401을 받음
- **THEN** 로그인 화면으로의 이동이 한 번만 발생해야 한다
- **AND** 최종 주소가 어떤 응답이 마지막에 도착했는지에 좌우되지 않아야 한다

#### Scenario: 복귀 주소에 쿼리 파라미터가 여러 개 있어도 보존된다
- **WHEN** `&`를 포함한 주소에서 401이 발생함
- **THEN** 로그인 후 그 주소가 파라미터를 모두 유지한 채 복원되어야 한다

#### Scenario: 로그인한 사용자의 상한 초과는 로그인 화면으로 보내지 않는다
- **WHEN** 로그인한 사용자가 즐겨찾기를 상한 초과로 추가해 403을 받음
- **THEN** 화면이 이동하지 않고 그 자리에 머물러야 한다
- **AND** 실패를 알리는 토스트가 떠야 한다
- **AND** 낙관적으로 바뀌었던 즐겨찾기 표시가 원래대로 되돌아가야 한다

#### Scenario: 서버가 준 거부 사유를 사용자가 볼 수 있다
- **WHEN** 플레이리스트 상한을 초과한 상태로 저장을 시도해 403을 받음
- **THEN** 서버 응답 본문의 `message`가 토스트로 표시되어야 한다

### Requirement: 로그인 화면은 복귀 주소가 없어도 로그인 완료 후 이동한다

시스템(프론트)은 로그인 화면에서 인증이 완료되면 **복귀 주소 전달 여부와 무관하게 화면을 이동시켜야(SHALL)** 한다. 복귀 주소가 없거나 비어 있으면 **메인 화면(`/`)으로 이동해야(SHALL)** 한다.

복귀 주소가 **현재 앱과 다른 origin이면 이동을 수행하지 않아야(SHALL NOT)** 하고, 잘못된 진입 경로임을 알리는 화면을 보여야(SHALL) 한다. 이 판정은 기본값 대체보다 **먼저** 이루어져야(SHALL) 한다.

#### Scenario: 복귀 주소 없이 로그인해도 메인으로 간다
- **WHEN** `/login`(파라미터 없음)에서 Discord 로그인을 완료함
- **THEN** 메인 화면(`/`)으로 이동해야 한다

#### Scenario: 복귀 주소가 있으면 그곳으로 돌아간다
- **WHEN** `/login?redirectUrl=<인코딩된 /playlists>`에서 Discord 로그인을 완료함
- **THEN** `/playlists`로 이동해야 한다

#### Scenario: 외부 origin은 기본값으로 대체하지 않고 차단한다
- **WHEN** `/login?redirectUrl=https://example.com/` 으로 진입함
- **THEN** "진입 경로가 잘못되었습니다" 화면이 보여야 한다
- **AND** 메인 화면으로 조용히 이동하지 않아야 한다
- **AND** 로그인 버튼이 노출되지 않아야 한다

### Requirement: 내 정보 적재는 렌더 밖에서 일어나고 동시 요청이 합쳐진다

시스템(프론트)은 로그인한 사용자 정보(`me`)를 **렌더 과정의 부수효과로 요청하지 않아야(SHALL NOT)** 한다. 적재 책임은 `me`를 보유한 전역 스토어가 가져야(SHALL) 한다.

이미 적재되어 있으면 **다시 요청하지 않아야(SHALL NOT)** 하고, 요청이 진행 중일 때 다시 요청되면 **진행 중인 요청을 재사용해야(SHALL)** 한다. 실패는 캐시하지 않아야(SHALL NOT) 하며, 적재 실패가 **미처리 rejection을 남기지 않아야(SHALL NOT)** 한다.

#### Scenario: 화면에 두 번 나타나도 요청은 한 번이다
- **WHEN** 로그인한 사용자가 메인 화면에 진입함
- **THEN** `/players/me` 요청이 한 번만 발생해야 한다

#### Scenario: 데스크톱·모바일 전환으로 재마운트되어도 다시 요청하지 않는다
- **WHEN** `me`가 적재된 상태에서 화면 폭을 바꿔 내 정보 표시가 재마운트됨
- **THEN** 추가 `/players/me` 요청이 발생하지 않아야 한다

#### Scenario: 적재 실패가 콘솔에 미처리 오류를 남기지 않는다
- **WHEN** `/players/me`가 네트워크 오류로 실패함
- **THEN** 미처리 Promise rejection이 보고되지 않아야 한다
