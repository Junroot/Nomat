# room-round-ui Specification

## Purpose

`PLAYING` 상태의 방에서 참가자가 보는 라운드 플레이 화면을 정의한다. 라운드의 권위는 전적으로 서버에 있으며, 프론트는 STOMP `/topic/rooms/{roomId}`로 오는 `ROUND_STARTED`·`ROUND_REVEALED`·`ENDED` 이벤트를 렌더링하고 서버의 다음 이벤트를 기다리는 표시 계층으로만 동작한다 — 승자 판정·라운드 전이·조기 종료를 프론트가 스스로 수행하지 않는다. 클립은 answer-stripped 재생 참조로 자동재생되며, 정답 추측은 별도 UI 없이 기존 채팅 입력을 재사용한다. 브라우저 자동재생 정책에 대응하는 1회 사용자 제스처 게이트, 임베드 재생 실패 감지·안내, `GET /rooms/{roomId}`의 `round` 스냅샷을 이용한 새로고침·재접속 복원을 포함한다.

## Requirements

### Requirement: ROUND_STARTED 수신 시 클립을 자동재생하고 남은 시간을 표시한다

시스템(프론트)은 STOMP `/topic/rooms/{roomId}`로 `ROUND_STARTED`를 받으면 answer-stripped 재생 참조(`embedId`·`startTimeSec`·`endTimeSec`·`repeatCount`)로 클립을 **자동재생**하고, `repeatCount`회 반복 후 정지해야(SHALL) 한다. 동시에 서버가 준 `deadlineAt`(epoch ms) 기준의 **표시용** 남은 시간을 보여야 하며, 남은 시간이 0에 도달해도 **로컬 시계로 라운드를 종료하지 않고** 서버의 다음 이벤트를 기다려야 한다. 라운드 번호는 `roundSeq / totalRounds`로 표시한다.

#### Scenario: ROUND_STARTED가 오면 클립이 자동재생되고 카운트다운이 시작된다
- **WHEN** `PLAYING` 화면에서 `type=ROUND_STARTED` 메시지를 수신
- **THEN** `currentTrack`(embedId·재생 구간)이 자동재생되고 `repeatCount`회 반복 후 정지해야 한다
- **AND** `roundSeq / totalRounds`와 `deadlineAt` 기준 남은 시간이 표시되어야 한다

#### Scenario: 남은 시간이 0이 되어도 로컬에서 라운드를 끝내지 않는다
- **WHEN** 표시용 카운트다운이 0에 도달했으나 아직 `ROUND_REVEALED`가 오지 않음
- **THEN** 화면은 "판정 중" 상태로 바뀌고 서버의 `ROUND_REVEALED`를 기다려야 한다
- **AND** 프론트가 스스로 승자 판정·다음 라운드 전이를 하지 않아야 한다

### Requirement: 게임 중 채팅 입력이 정답 추측이며 별도 정답 입력 UI가 없다

시스템은 `PLAYING` 동안 채팅 입력·피드를 화면에 노출해야(SHALL) 하며, 참가자의 채팅 전송(`/app/rooms/chat`)이 곧 정답 추측이다. 정답 판정은 서버가 수행하므로 프론트는 별도의 정답 입력 컴포넌트를 만들지 않고 기존 채팅 입력을 재사용한다. 서버가 채팅 원문을 항상 방송하므로 추측은 피드에 그대로 표시된다.

#### Scenario: 게임 중에도 채팅 입력과 피드가 보인다
- **WHEN** 방이 `PLAYING`으로 전이됨
- **THEN** 채팅 입력창과 메시지 피드가 계속 표시되어야 한다 (플레이스홀더로 숨기지 않는다)

#### Scenario: 추측 채팅이 피드에 나타난다
- **WHEN** 참가자가 `PLAYING` 중 채팅을 전송하고 서버가 `CHAT`을 방송
- **THEN** 그 메시지가 추측 피드에 표시되어야 한다 (정답 여부와 무관하게)

### Requirement: ROUND_REVEALED 수신 시 정답·승자·점수판을 표시한다

시스템은 `ROUND_REVEALED`를 받으면 정규 정답(`title`)·승자(`winnerId`)·갱신된 점수판(`scores`)을 표시해야(SHALL) 한다. 승자가 없으면(`winnerId=null`, 타임아웃) 정답과 함께 시간 초과로 표시한다. 점수판은 id만 담고 있으므로 방의 `players`와 조인해 닉네임으로 표기하고, 미매칭 id는 퇴장으로 폴백한다.

정답 공개 구간에는 **정답 곡을 클립 시작 지점부터 다시 재생해야(SHALL) 한다.** 이전 요구사항은 이 시점에 "클립을 정지"하도록 규정했으나, 그러면 참가자가 정답을 텍스트로만 확인하고 **곡을 듣지 못한 채** 다음 라운드로 넘어간다. 특히 타임아웃으로 공개된 라운드는 클립이 이미 소진돼 있어(`openDuration = 클립 길이 × repeatCount + 여유`) 정지 여부와 무관하게 무음이 된다 — 아무도 맞히지 못한 곡일수록 들려줄 필요가 큰데 정확히 그 경우에 들리지 않았다.

이 재생은 다음 라운드 선버퍼링과 **동시에 성립해야(SHALL) 한다.** 선버퍼링은 다음 곡을 실제로 적재해 버퍼를 채우는 방식이라 하나의 플레이어로는 현재 곡 재생과 양립할 수 없다. 구현 방식은 `design.md` Decision 4를 따른다.

정답 공개 구간에는 **정답 곡의 영상을 화면에 표시해야(SHALL) 한다.** 다만 노출 범위는 엄격히 제한된다:

- `OPEN` 동안에는 영상을 **표시해서는 안 된다(SHALL NOT)** — 썸네일과 영상 제목이 곧 정답이므로 표시하면 게임이 성립하지 않는다
- 선버퍼링 중인 플레이어의 영상도 **표시해서는 안 된다(SHALL NOT)** — 다음 라운드의 곡을 물고 있어 표시하면 다음 정답이 유출된다

즉 표시 대상은 **정답 공개 구간의 재생 담당 플레이어 하나뿐**이다.

#### Scenario: 승자가 있으면 정답과 승자를 표시한다
- **WHEN** `type=ROUND_REVEALED`를 수신(`winnerId` 존재)
- **THEN** 정답(`title`)과 승자 닉네임, 갱신된 점수판이 표시되어야 한다

#### Scenario: 타임아웃이면 정답과 시간 초과를 표시한다
- **WHEN** `type=ROUND_REVEALED`를 수신하고 `winnerId`가 null
- **THEN** 정답과 함께 아무도 맞히지 못했음이 표시되어야 한다

#### Scenario: 정답 공개 구간에 정답 곡이 들린다
- **WHEN** 라운드가 `REVEAL`로 전이됨
- **THEN** 정답 곡이 클립 시작 지점부터 다시 재생되어야 한다
- **AND** 아무도 맞히지 못해 클립이 이미 소진된 라운드에서도 들려야 한다
- **AND** 같은 구간에 다음 라운드 트랙의 선버퍼링이 함께 진행되어야 한다

#### Scenario: 정답 공개 구간에만 영상이 보인다
- **WHEN** 라운드가 `REVEAL`로 전이됨
- **THEN** 정답 곡의 영상이 정답·승자 정보와 함께 화면에 표시되어야 한다
- **AND** 선버퍼링 중인 다음 곡의 영상은 표시되지 않아야 한다

#### Scenario: OPEN 중에는 영상이 보이지 않는다
- **WHEN** 라운드가 `OPEN`이고 클립이 재생 중임
- **THEN** 영상이 화면에 표시되지 않아야 한다 (썸네일·제목이 정답을 노출하므로)

### Requirement: 게임 종료 시 마지막 점수로 최종 결과 화면을 보여준다

시스템은 `ENDED`를 받으면 게임 종료로 처리하고, 직전 `ROUND_REVEALED`가 전달한 마지막 점수판(sticky 보존)으로 **최종 결과(순위) 화면**을 표시해야(SHALL) 한다. `ENDED` 메시지에는 점수판이 실리지 않으므로 프론트가 마지막 `scores`를 유지해 사용한다. `ENDED`는 행위자 유무(방장 수동 종료 vs 서버 주도 자연 종료)와 무관하게 게임 종료로 처리한다. 종료 후 방 상태는 `ACTIVE`로 복귀한다.

#### Scenario: 게임이 끝나면 최종 순위가 표시된다
- **WHEN** `type=ENDED`를 수신
- **THEN** 마지막 `ROUND_REVEALED`의 점수판으로 순위(닉네임·점수)와 우승자 하이라이트가 표시되어야 한다
- **AND** 방 상태가 `ACTIVE`로 복귀해 로비로 돌아갈 수 있어야 한다

#### Scenario: 서버 주도 종료도 행위자 없이 결과를 보여준다
- **WHEN** 라운드 엔진이 서버 주도로 종료해 행위자(`playerId`/`nickname`) 없는 `ENDED`가 도착
- **THEN** 행위자 유무와 무관하게 최종 결과 화면이 표시되어야 한다

### Requirement: 재접속·새로고침 시 라운드 스냅샷으로 화면을 복원한다

시스템은 `PLAYING` 중 새로고침하거나 재접속하면 `GET /rooms/{roomId}` 응답의 `round` 스냅샷으로 현재 라운드 화면을 복원해야(SHALL) 한다. `OPEN`이면 정답 없이 클립·카운트다운·점수판을 복원하고, `REVEAL`/`ENDED`면 정답을 포함해 복원한다. 늦게 도착한 스냅샷이 더 진행된 라이브 상태를 되돌리지 않도록 `roundSeq` 단조 증가를 보장한다.

#### Scenario: OPEN 중 재접속은 정답 없이 복원된다
- **WHEN** `OPEN` 라운드 진행 중 새로고침해 `round.phase=OPEN` 스냅샷을 받음
- **THEN** 클립·남은 시간·점수판이 복원되고 정답(`title`)은 표시되지 않아야 한다

#### Scenario: REVEAL 중 재접속은 정답까지 복원된다
- **WHEN** 재접속 시 `round.phase=REVEAL` 스냅샷(`title` 포함)을 받음
- **THEN** 정답·승자·점수판이 공개 상태로 복원되어야 한다

### Requirement: 오디오 자동재생을 위해 사용자 제스처 게이트를 제공한다

시스템은 `PLAYING` 진입 시 오디오 자동재생이 브라우저 정책에 막히지 않도록 **1회 사용자 제스처 게이트**(예: "게임 참여 / 소리 켜기")를 제공해야(SHALL) 한다. 게이트 클릭으로 플레이어를 arming한 뒤에는 이후 라운드가 조용히 자동재생된다. 재접속으로 `PLAYING`을 복원할 때도 동일하게 게이트를 거친다. 음소거 자동재생은 노래 맞히기에 부적합하므로 사용하지 않는다.

단, arming 이후에도 브라우저가 자동재생을 차단할 수 있다. 플레이어가 **자동재생 차단을 통지하면**(IFrame API `onAutoplayBlocked`) arming이 소실된 것으로 보고, 요구사항 "클립이 재생되지 않으면 감지해 사용자에게 알린다"에 따라 제스처를 다시 유도한다.

#### Scenario: PLAYING 진입 시 제스처 게이트가 뜬다
- **WHEN** 참가자 화면이 `PLAYING`으로 전이되고 아직 arming되지 않음
- **THEN** 오디오 재생을 위한 1회 제스처 게이트가 표시되어야 한다

#### Scenario: 게이트를 통과하면 이후 라운드가 자동재생된다
- **WHEN** 사용자가 제스처 게이트를 클릭해 arming
- **THEN** 현재 및 이후 `ROUND_STARTED`의 클립이 추가 제스처 없이 자동재생되어야 한다

### Requirement: 클립이 재생되지 않으면 감지해 사용자에게 알린다

시스템은 arming된 상태에서 클립 재생을 시도했는데 재생이 시작되지 않으면 이를 **감지해 재생 불가를 화면에 알려야(SHALL)** 한다. 일부 YouTube 트랙은 임베드 플레이어에서 재생이 거부되며(콘텐츠 경고·임베드 차단 등) 이때 `onError`가 발생하지 않을 수 있으므로, 오류 이벤트만으로 판정하지 않고 **재생 개시 여부를 관찰**해 판정한다.

판정 규칙은 다음과 같다. 재생 시도 후 **3초** 안에 재생 개시(`PLAYING`)도 버퍼링 진입(`BUFFERING`)도 관찰되지 않으면 재생 불가로 판정한다. 오류 이벤트가 오면 3초를 기다리지 않고 즉시 판정한다. **버퍼링 진입은 플레이어 생존 신호**이므로 관찰되면 판정을 해제한다 — 느린 네트워크를 재생 불가로 오판하지 않기 위함이다. 3초는 최소 클립 예산(`clipLen × repeatCount + 2s`)이 약 17초임을 전제로, 안내를 보여줄 시간을 남기면서 버퍼링 신호가 도달하기에 충분한 값으로 정했다.

안내는 사용자가 자신의 오디오 설정을 의심하지 않도록 **"이 곡이 재생되지 않는다"는 사실을 명시**해야 하며, 브라우저 자동재생 정책에 막힌 경우(제스처 게이트로 해결 가능)와 **구분되는 안내**를 제공해야 한다.

재생 실패는 라운드 진행에 영향을 주지 않는다 — 라운드의 권위는 서버이므로 프론트는 재생 실패를 이유로 라운드를 종료·스킵하지 않고 서버의 `ROUND_REVEALED`를 그대로 기다린다.

#### Scenario: 재생이 시작되지 않으면 재생 불가를 알린다
- **WHEN** arming된 상태에서 클립 재생을 시도했으나 재생 개시도 버퍼링 진입도 관찰되지 않은 채 3초가 경과
- **THEN** 해당 곡을 재생할 수 없다는 안내가 표시되어야 한다
- **AND** 안내는 사용자의 오디오 설정 문제가 아님이 드러나야 한다

#### Scenario: 오류 이벤트가 오면 기다리지 않고 즉시 알린다
- **WHEN** 플레이어가 재생 불가를 나타내는 오류 이벤트를 발생시킴
- **THEN** 3초를 기다리지 않고 즉시 재생 불가 안내가 표시되어야 한다

#### Scenario: 버퍼링에 진입한 느린 재생은 재생 불가로 판정하지 않는다
- **WHEN** 클립이 버퍼링에 진입했으나 네트워크가 느려 3초 안에 재생이 시작되지 않음
- **THEN** 재생 불가 안내가 표시되지 않아야 한다
- **AND** 재생이 시작되면 정상적으로 클립이 들려야 한다

#### Scenario: 자동재생 정책 차단은 재생 불가와 구분한다
- **WHEN** 플레이어가 자동재생 차단을 통지(`onAutoplayBlocked`)
- **THEN** 재생 불가 안내가 아니라 소리 켜기를 다시 유도하는 안내가 표시되어야 한다

#### Scenario: 재생에 실패해도 라운드는 서버 권위로 계속된다
- **WHEN** 클립 재생에 실패한 채로 라운드가 진행 중
- **THEN** 카운트다운과 추측 채팅은 그대로 동작해야 한다
- **AND** 프론트가 라운드를 스스로 종료·스킵하지 않고 서버의 `ROUND_REVEALED`로 정답이 공개되어야 한다

### Requirement: 오디오 플레이어 초기화는 게임이 시작되기 전에 끝나야 한다

오디오 플레이어의 초기화 비용(아이프레임 생성·플레이어 부트스트랩)은 **어느 라운드도 부담해서는 안 된다(SHALL NOT)**. 이 비용은 어떤 곡을 재생할지 몰라도 치를 수 있으므로, 시스템(프론트)은 방에 입장한 시점 — 즉 게임이 시작되기 전 — 에 플레이어를 준비해야(SHALL) 한다. 플레이어 인스턴스는 방 세션 동안 유지되며 라운드마다 다시 만들어져서는 안 된다(SHALL NOT).

첫 라운드가 특별히 느려서는 안 된다는 것이 이 요구사항의 요지다. 첫 라운드 앞에는 정답을 노출하지 않고 트랙을 미리 받을 수 있는 구간이 없어 로드·버퍼링은 회수할 수 없지만, 부트스트랩은 트랙과 무관하므로 회수할 수 있다.

플레이어 인스턴스를 라운드 간에 유지하므로, 라운드 경계에서 초기화되어야 할 재생 상태는 명시적으로 초기화되어야(SHALL) 한다 — 반복 재생 카운터와 재생 가능 여부 판정은 라운드가 바뀔 때마다 새로 서야 한다.

> 영상 로드·버퍼링 구간은 본 요구사항이 아니라 아래 "클라이언트는 다음 라운드 트랙을 정답 공개 구간 동안 미리 버퍼링한다"가 다룬다.

#### Scenario: 게임 시작 전에 플레이어가 준비된다
- **WHEN** 멤버가 방에 입장해 아직 게임이 시작되지 않음
- **THEN** 오디오 플레이어가 이미 생성되어 재생 준비를 마쳐야 한다
- **AND** 이 시점에는 어떤 곡도 적재되어 있지 않아야 한다 (첫 라운드 정답이 노출되면 안 된다)

#### Scenario: 첫 라운드도 부트스트랩 비용을 부담하지 않는다
- **WHEN** `ROUND_STARTED`로 첫 라운드가 열림
- **THEN** 아이프레임 생성·플레이어 부트스트랩이 이 구간에서 발생하지 않아야 한다
- **AND** `ROUND_STARTED` 수신부터 재생 개시까지의 지연이 영상 로드·버퍼링 시간에 그쳐야 한다

#### Scenario: 라운드가 바뀌어도 플레이어를 다시 만들지 않는다
- **WHEN** 라운드가 전환되어 새 트랙으로 교체됨
- **THEN** 기존 플레이어 인스턴스에 곡만 교체되어야 하며 아이프레임이 다시 생성되어서는 안 된다

#### Scenario: 라운드가 바뀌면 반복 카운터가 초기화된다
- **WHEN** `repeatCount`만큼 재생을 마친 라운드에 이어 다음 라운드가 열림
- **THEN** 새 트랙이 `repeatCount`회 온전히 반복되어야 한다 (이전 라운드의 소진 카운트가 이월되지 않는다)

#### Scenario: 라운드가 바뀌면 재생 불가 판정이 새로 선다
- **WHEN** 이전 라운드에서 재생 불가(`unplayable`)로 판정된 뒤 다음 라운드가 열림
- **THEN** 새 트랙에 대해 재생 불가 판정이 처음부터 다시 수행되어야 한다
- **AND** 이전 라운드의 판정 결과가 새 라운드의 안내 UI에 남아 있지 않아야 한다

### Requirement: 클라이언트는 다음 라운드 트랙을 정답 공개 구간 동안 미리 버퍼링한다

클라이언트는 다음 라운드의 재생 참조를 받으면 — `ROUND_REVEALED` 이벤트로든 `REVEAL` 단계의 재접속 스냅샷으로든 — 정답 공개 구간 동안 그 트랙의 버퍼링을 시작해야(SHALL) 한다. 이로써 다음 라운드가 열릴 때 영상 로드·버퍼링이 이미 완료되어 있어야 한다.

선버퍼링된 트랙은 해당 라운드가 열리기 전까지 **소리를 내서는 안 된다(SHALL NOT)**. 정답 공개 구간에 다음 곡이 들리면 그 자체로 정답이 유출된다. 이 구간에는 정답 곡이 함께 재생되므로(위 `ROUND_REVEALED` 요구사항) 두 소리가 섞이지 않도록 선버퍼링 쪽은 반드시 음소거되어야 한다.

선버퍼링이 유발하는 플레이어 상태 전이는 **현재 라운드의 반복 재생 카운터와 재생 불가 판정에 영향을 주어서는 안 된다(SHALL NOT)**. 기존 요구사항이 버퍼링 진입을 "플레이어 생존 신호"로 삼아 재생 불가 판정을 해제하도록 규정하고 있어, 선버퍼링이 만든 전이를 구분하지 않으면 다음 라운드의 판정이 관찰도 하기 전에 해제되거나 반복 카운터가 잘못 소진된다.

> 재생 참조를 서버가 어느 시점에 어떤 형태로 내려보내는지(그리고 마지막 라운드에서 비어 있어야 한다는 경계 조건)는 서버 계약이므로 `room-game-session`의 요구사항이 다룬다.

#### Scenario: 다음 트랙을 받으면 즉시 버퍼링을 시작한다
- **WHEN** 클라이언트가 `ROUND_REVEALED` 또는 `REVEAL` 단계 스냅샷으로 다음 라운드의 재생 참조를 받음
- **THEN** 해당 트랙의 버퍼링을 즉시 시작해야 한다
- **AND** 버퍼링 중 소리가 나지 않아야 한다

#### Scenario: 선버퍼링 상태 전이는 현재 라운드의 판정을 건드리지 않는다
- **WHEN** 선버퍼링으로 플레이어에 `BUFFERING`·`PLAYING` 등의 상태 전이가 발생함
- **THEN** 현재 라운드의 반복 재생 카운터가 증가하지 않아야 한다
- **AND** 다음 라운드의 재생 불가 판정이 그 전이만으로 해제되지 않아야 한다

#### Scenario: 다음 트랙이 없으면 선버퍼링하지 않는다
- **WHEN** 마지막 라운드의 `ROUND_REVEALED`를 받아 다음 재생 참조가 비어 있음
- **THEN** 선버퍼링을 시도하지 않아야 하며 오류 없이 게임 종료로 진행되어야 한다

#### Scenario: 선버퍼링된 라운드는 로드 지연 없이 재생을 시작한다
- **WHEN** 선버퍼링을 마친 트랙의 라운드가 `ROUND_STARTED`로 열림
- **THEN** `ROUND_STARTED` 수신부터 재생 개시까지의 지연이 **500ms 이내**여야 한다

> 500ms는 기준선 1821ms에서 로드·버퍼링 1363ms가 선버퍼링으로 제거되고 부트스트랩 458ms도 플레이어 재사용으로 사라진다는 계산에 근거한 잠정치다. 태스크 6.2에서 실측이 갱신되면 위 요구사항의 70% 임계와 함께 재검토한다.
