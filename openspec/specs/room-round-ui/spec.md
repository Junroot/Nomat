# room-round-ui Specification

## Purpose

`PLAYING` 상태의 방에서 참가자가 보는 라운드 플레이 화면을 정의한다. 라운드의 권위는 전적으로 서버에 있으며, 프론트는 STOMP `/topic/rooms/{roomId}`로 오는 `ROUND_STARTED`·`ROUND_REVEALED`·`ENDED` 이벤트를 렌더링하고 서버의 다음 이벤트를 기다리는 표시 계층으로만 동작한다 — 승자 판정·라운드 전이·조기 종료를 프론트가 스스로 수행하지 않는다. 클립은 answer-stripped 재생 참조로 자동재생되며, 정답 추측은 별도 UI 없이 기존 채팅 입력을 재사용한다. 브라우저 자동재생 정책에 대응하는 1회 사용자 제스처 게이트, 임베드 재생 실패 감지·안내, `GET /rooms/{roomId}`의 `round` 스냅샷을 이용한 새로고침·재접속 복원을 포함한다.

## Requirements

### Requirement: ROUND_STARTED 수신 시 클립을 자동재생하고 남은 시간을 표시한다

시스템(프론트)은 STOMP `/topic/rooms/{roomId}`로 `ROUND_STARTED`를 받으면 answer-stripped 재생 참조(`embedId`·`startTimeSec`·`endTimeSec`·`repeatCount`)로 클립을 **자동재생**하고, `repeatCount`회 반복 후 정지해야(SHALL) 한다. 동시에 서버가 준 `deadlineAt`(epoch ms) 기준의 **표시용** 남은 시간을 보여야 하며, 남은 시간이 0에 도달해도 **로컬 시계로 라운드를 종료하지 않고** 서버의 다음 이벤트를 기다려야 한다. 라운드 번호는 `roundSeq / totalRounds`로 표시한다.

#### Scenario: ROUND_STARTED가 오면 클립이 자동재생되고 카운트다운이 시작된다
- **WHEN** `PLAYING` 화면에서 `type=ROUND_STARTED` 메시지를 수신
- **THEN** `currentTrack`(embedId·재생 구간)이 자동재생되고 `repeatCount`회 반복 후 정지해야 한다
- **AND** `roundSeq / totalRounds`와 `deadlineAt` 기준 남은 시간이 표시되어야 한다

#### Scenario: 남은 시간이 0이 되어도 로컬에서 라운드를 끝내지 않는다
- **WHEN** 표시용 카운트다운이 0에 도달했으나 아직 `ROUND_REVEALED`가 오지 않음
- **THEN** 화면은 "판정 중" 상태로 바뀌고 서버의 `ROUND_REVEALED`를 기다려야 한다
- **AND** 프론트가 스스로 승자 판정·다음 라운드 전이를 하지 않아야 한다

### Requirement: 게임 중 채팅 입력이 정답 추측이며 별도 정답 입력 UI가 없다

시스템은 `PLAYING` 동안 채팅 입력·피드를 화면에 노출해야(SHALL) 하며, 참가자의 채팅 전송(`/app/rooms/chat`)이 곧 정답 추측이다. 정답 판정은 서버가 수행하므로 프론트는 별도의 정답 입력 컴포넌트를 만들지 않고 기존 채팅 입력을 재사용한다. 서버가 채팅 원문을 항상 방송하므로 추측은 피드에 그대로 표시된다.

이 노출은 `OPEN`뿐 아니라 **정답 공개(`REVEAL`) 구간에도 유지되어야(SHALL) 한다.** 정답 공개 UI가 채팅 피드나 입력창을 **가려서는 안 되며(SHALL NOT)**, 그 구간에도 입력과 전송이 계속 가능해야(SHALL) 한다.

서버는 라운드 단계와 무관하게 채팅을 방송하고 정답 판정만 `OPEN`에서 수행하므로, 공개 구간의 채팅 차단은 서버 계약이 요구하는 바가 아니라 **클라이언트가 스스로 만드는 손실**이다. 정답이 공개된 직후는 참가자들의 반응이 오가는 구간이므로 이 시간의 대화를 막을 이유가 없다.

#### Scenario: 게임 중에도 채팅 입력과 피드가 보인다
- **WHEN** 방이 `PLAYING`으로 전이됨
- **THEN** 채팅 입력창과 메시지 피드가 계속 표시되어야 한다 (플레이스홀더로 숨기지 않는다)

#### Scenario: 추측 채팅이 피드에 나타난다
- **WHEN** 참가자가 `PLAYING` 중 채팅을 전송하고 서버가 `CHAT`을 방송
- **THEN** 그 메시지가 추측 피드에 표시되어야 한다 (정답 여부와 무관하게)

#### Scenario: 정답 공개 구간에도 채팅이 가려지지 않는다
- **WHEN** 라운드가 `REVEAL`로 전이되어 정답·승자·영상이 표시됨
- **THEN** 채팅 피드와 입력창이 계속 보여야 한다
- **AND** 어떤 표시 요소도 그것들을 덮지 않아야 한다

#### Scenario: 정답 공개 구간에 보낸 채팅이 피드에 나타난다
- **WHEN** 참가자가 `REVEAL` 구간에 채팅을 입력해 전송
- **THEN** 입력과 전송이 정상 동작해야 한다
- **AND** 서버가 방송한 그 메시지가 피드에 표시되어야 한다

### Requirement: OPEN 구간에 포기 컨트롤을 표시하고 키보드로 조작할 수 있다

시스템(프론트)은 라운드가 `OPEN`인 동안 **포기("모르겠어요") 컨트롤을 표시해야(SHALL) 한다.** 데스크톱에서는 **`Shift+Enter`**로 조작할 수 있어야(SHALL) 하며, 조합키가 없는 환경을 위해 컨트롤 자체도 누를 수 있어야(SHALL) 한다.

**키보드가 주 경로인 이유**: `OPEN` 동안 참가자의 포커스는 이미 채팅 입력창에 있다 — 추측을 거기에 치기 때문이다. 조작 수단이 버튼뿐이면 마우스로 손을 옮겼다가 돌아와야 해 추측의 리듬이 끊긴다.

키 처리는 **IME 조합 중에는 발화하지 않아야(SHALL NOT) 한다.** 한국어·일본어 입력에서 조합 중의 `Enter`는 조합 확정이므로, 그 입력이 포기로 해석되면 글자를 확정하려던 참가자가 의도치 않게 포기한다. 기존 채팅 전송이 쓰는 것과 같은 조합 상태 판정을 적용한다.

포기 신호에는 **현재 라운드 식별자를 실어 보내야(SHALL) 한다** — 서버가 라운드 경계에서 늦게 도착한 신호를 거를 수 있도록 한다.

컨트롤은 **포기 인원이 0명일 때에도 표시되어야(SHALL) 한다.** 현황이 생겼을 때만 표시하면 "아무도 누르지 않음 → 현황이 뜨지 않음 → 기능의 존재를 모름 → 아무도 누르지 않음"의 순환에 빠져, 첫 번째로 누를 사람이 기능을 영원히 발견하지 못한다.

컨트롤은 **채팅 입력창을 덮어서는 안 되며(SHALL NOT)**, 전송 버튼과 혼동되지 않는 위치에 두어야(SHALL) 한다. 채팅 피드에 **겹쳐 놓아도 되지만(MAY), 가장 최근 메시지를 가려서는 안 된다(SHALL NOT)** — 대화의 맨 아래를 보고 있는 참가자에게는 방금 도착한 메시지가 항상 온전히 보여야 한다. 겹쳐 놓는 경우 컨트롤이 차지할 자리를 피드 하단에 미리 확보하는 식으로 이를 보장한다.

컨트롤이 나타나고 사라지는 것이 **채팅 피드의 표시 영역을 바꿔서는 안 된다(SHALL NOT).** 라운드는 `OPEN`과 `REVEAL`을 반복하므로, 컨트롤의 자리가 그때마다 생겼다 사라지면 읽고 있던 메시지가 라운드마다 두 번씩 위아래로 튄다.

컨트롤의 시각적 강도는 **낮게 유지해야(SHALL) 한다.** 눈에 띄게 강조하면 습관적으로 누르게 되어, 정말 모르는 경우에만 누른다는 전제가 무너진다. 억제해야 할 것은 크기가 아니라 유인이다.

라운드가 `OPEN`이 아닌 동안에는 컨트롤을 **표시하지 않아야(SHALL NOT) 한다** — 정답 공개·종료 구간에는 포기할 대상이 없다.

#### Scenario: OPEN 중 포기 컨트롤이 보인다
- **WHEN** 라운드가 `OPEN`이고 아직 아무도 포기하지 않음
- **THEN** 포기 컨트롤이 화면에 표시되어야 한다
- **AND** 가장 최근 메시지와 채팅 입력창이 가려지지 않아야 한다

#### Scenario: 라운드가 전이돼도 채팅 피드가 흔들리지 않는다
- **WHEN** 라운드가 `OPEN`에서 `REVEAL`로, 다시 다음 `OPEN`으로 전이되어 포기 컨트롤이 사라졌다 나타남
- **THEN** 채팅 피드의 표시 영역 높이가 변하지 않아 읽고 있던 메시지의 위치가 유지되어야 한다

#### Scenario: Shift+Enter로 포기한다
- **WHEN** 참가자가 채팅 입력창에 포커스를 둔 채 `Shift+Enter`를 입력
- **THEN** 현재 라운드 식별자와 함께 포기 신호가 전송되어야 한다
- **AND** 채팅 메시지는 전송되지 않아야 한다

#### Scenario: Shift 없는 Enter는 기존대로 채팅을 보낸다
- **WHEN** 참가자가 채팅 입력창에서 `Enter`만 입력
- **THEN** 기존과 동일하게 채팅이 전송되어야 한다
- **AND** 포기 신호가 전송되지 않아야 한다

#### Scenario: IME 조합 중의 입력은 포기로 해석되지 않는다
- **WHEN** 한글·일본어 조합이 진행 중인 상태에서 `Shift+Enter`가 입력됨
- **THEN** 포기 신호가 전송되지 않아야 한다

#### Scenario: 조합키가 없는 환경에서도 컨트롤을 누를 수 있다
- **WHEN** 모바일 등 조합키를 쓸 수 없는 환경의 참가자가 포기 컨트롤을 누름
- **THEN** 키보드 조작과 동일하게 포기 신호가 전송되어야 한다

#### Scenario: OPEN이 아니면 컨트롤이 사라진다
- **WHEN** 라운드가 `REVEAL`로 전이되거나 게임이 종료됨
- **THEN** 포기 컨트롤이 표시되지 않아야 한다

### Requirement: 포기 현황을 인원수로 표시하고 본인 상태를 구분한다

시스템은 서버가 전파한 **포기 인원수와 전이에 필요한 인원수**를 표시해야(SHALL) 하며, **본인이 포기 상태인지 여부를 시각적으로 구분해야(SHALL) 한다.** 포기는 토글이므로 "내가 눌렀는가"가 항상 명확해야 취소 여부를 판단할 수 있다.

**누가 포기했는지는 표시하지 않아야(SHALL NOT) 한다** — 서버가 명단을 보내지 않으며, 다른 경로로 유추해 표시해서도 안 된다.

포기 인원수는 토글로 **줄어들 수도 있으므로**, 같은 라운드 안에서 받은 마지막 값을 그대로 표시해야(SHALL) 한다. 최댓값을 유지하는 방식으로 처리해서는 안 된다(SHALL NOT) — 취소가 영영 반영되지 않는다.

**라운드가 바뀌면 표시가 초기화되어야(SHALL) 한다.** 이전 라운드의 인원수나 본인 포기 상태가 새 라운드로 이월되어서는 안 된다(SHALL NOT).

현황 표시는 컨트롤과 **같은 자리에서 갱신되어야(SHALL) 한다.** 인원수가 생겼다고 새 요소가 나타나 레이아웃이 밀리면, 정답을 입력하려던 참가자의 시선과 클릭 지점이 그 순간에 흔들린다.

#### Scenario: 다른 참가자가 포기하면 인원수가 갱신된다
- **WHEN** 포기 현황 전파를 수신
- **THEN** 포기 인원수와 필요 인원수가 갱신되어 표시되어야 한다

#### Scenario: 내가 포기한 상태가 구분되어 보인다
- **WHEN** 참가자 본인이 포기함
- **THEN** 컨트롤이 포기 상태로 표시되어 취소할 수 있음을 알 수 있어야 한다

#### Scenario: 포기 취소로 인원수가 줄어드는 것이 반영된다
- **WHEN** 포기 인원수가 이전보다 작은 값으로 전파됨
- **THEN** 줄어든 값이 그대로 표시되어야 한다 (이전 최댓값이 유지되어서는 안 된다)

#### Scenario: 라운드가 바뀌면 현황이 초기화된다
- **WHEN** 새 라운드가 `ROUND_STARTED`로 열림
- **THEN** 포기 인원수가 0으로, 본인 포기 상태가 해제로 표시되어야 한다

#### Scenario: 포기자 명단이 표시되지 않는다
- **WHEN** 여러 참가자가 포기한 상태
- **THEN** 누가 포기했는지를 나타내는 표시가 없어야 한다

### Requirement: 포기 조작 방법을 발견할 수 있도록 안내한다

시스템은 참가자가 **포기 단축키의 존재를 알 수 있도록 안내해야(SHALL) 한다.** 단축키는 그 자체로 발견 가능성이 없고, 마우스를 올려야 드러나는 안내(툴팁 등)는 키보드가 주 경로라는 전제와 모순되므로 안내 수단으로 삼지 않는다(SHALL NOT).

안내는 다음 두 곳에서 이루어진다.

1. **포기 컨트롤 자체**가 단축키 표기를 함께 담는다. 조합키를 쓸 수 없는 환경에서는 단축키 표기를 **감춰야(SHALL) 한다** — 그 환경에서 `Shift+Enter`는 사실이 아니다.
2. **오디오 제스처 게이트**가 게임 진입 시 조작 방법을 한 번 알린다. 이 게이트는 `PLAYING` 진입·재접속 시 모든 참가자가 반드시 통과하므로 도달률이 완전하다. 안내 문구는 실행 환경에 맞게 달라져야(SHALL) 한다.

또한 게임 중 채팅 입력의 안내 문구는 **그 입력이 정답 제출임을 드러내야(SHALL) 한다.** `PLAYING` 동안의 채팅은 잡담이 아니라 정답 추측인데, 일반 상태와 같은 문구를 쓰면 그 사실이 전달되지 않는다.

#### Scenario: 컨트롤이 단축키를 함께 보여준다
- **WHEN** 데스크톱 환경에서 라운드가 `OPEN`임
- **THEN** 포기 컨트롤에 `Shift+Enter` 표기가 함께 보여야 한다

#### Scenario: 조합키를 쓸 수 없는 환경에서는 단축키 표기가 숨겨진다
- **WHEN** 모바일 등 조합키를 쓸 수 없는 화면 폭에서 라운드가 `OPEN`임
- **THEN** 단축키 표기가 보이지 않아야 한다
- **AND** 포기 컨트롤 자체는 계속 보여야 한다

#### Scenario: 게임 진입 시 조작 방법이 안내된다
- **WHEN** 참가자가 `PLAYING` 진입으로 오디오 제스처 게이트를 마주함
- **THEN** 정답을 채팅으로 입력한다는 안내와 포기 조작 방법이 함께 표시되어야 한다
- **AND** 안내 문구가 실행 환경(조합키 사용 가능 여부)에 맞아야 한다

#### Scenario: 게임 중 채팅 입력이 정답 제출임을 알린다
- **WHEN** 방이 `PLAYING` 상태임
- **THEN** 채팅 입력의 안내 문구가 정답 입력임을 드러내야 한다

### Requirement: ROUND_REVEALED 수신 시 정답·승자·점수판을 표시한다

시스템은 `ROUND_REVEALED`를 받으면 정규 정답(`title`)·승자(`winnerId`)·갱신된 점수판(`scores`)을 표시해야(SHALL) 한다. 승자가 없으면(`winnerId=null`, 타임아웃) 정답과 함께 시간 초과로 표시한다.

점수판 항목과 승자 이름은 **서버가 해석해 보낸 닉네임**(`scores[].nickname`·`winnerNickname`)을 그대로 표기해야(SHALL) 하며, 방의 현재 멤버 목록(`players`)과 조인해서는 안 된다(SHALL NOT). 멤버 목록은 퇴장 즉시 줄어드는 반면 점수판은 다음 공개까지(종료 후에는 영구히) 유지되므로, 둘을 조인하면 **이미 떠난 참가자의 이름이 사라진다.** `nickname`을 해석할 수 없는 경우에만 중립 라벨로 대체하며, 퇴장을 단정하는 표기는 쓰지 않는다.

정답 공개 구간에는 **정답 곡을 클립 시작 지점부터 다시 재생해야(SHALL) 한다.** 이전 요구사항은 이 시점에 "클립을 정지"하도록 규정했으나, 그러면 참가자가 정답을 텍스트로만 확인하고 **곡을 듣지 못한 채** 다음 라운드로 넘어간다. 특히 타임아웃으로 공개된 라운드는 클립이 이미 소진돼 있어(`openDuration = 클립 길이 × repeatCount + 여유`) 정지 여부와 무관하게 무음이 된다 — 아무도 맞히지 못한 곡일수록 들려줄 필요가 큰데 정확히 그 경우에 들리지 않았다.

이 재생은 다음 라운드 선버퍼링과 **동시에 성립해야(SHALL) 한다.** 선버퍼링은 다음 곡을 실제로 적재해 버퍼를 채우는 방식이라 하나의 플레이어로는 현재 곡 재생과 양립할 수 없다. 구현 방식은 `add-room-round-frontend`·`reduce-round-playback-latency`의 `design.md` Decision 4를 따른다.

정답 공개 구간에는 **정답 곡의 영상을 화면에 표시해야(SHALL) 한다.** 다만 노출 범위는 엄격히 제한된다:

- `OPEN` 동안에는 영상을 **표시해서는 안 된다(SHALL NOT)** — 썸네일과 영상 제목이 곧 정답이므로 표시하면 게임이 성립하지 않는다
- 선버퍼링 중인 플레이어의 영상도 **표시해서는 안 된다(SHALL NOT)** — 다음 라운드의 곡을 물고 있어 표시하면 다음 정답이 유출된다
- 오디오 제스처 게이트가 표시 중인 동안에도 영상을 **표시해서는 안 된다(SHALL NOT)** — 게이트를 통과하기 전에는 재생이 시작되지 않았으므로, 아직 아무것도 일어나지 않은 영상이 차단 화면 뒤에 비칠 뿐이다

즉 표시 대상은 **정답 공개 구간의 재생 담당 플레이어 하나뿐**이다.

**정답 공개 UI는 화면을 점유해서는 안 된다(SHALL NOT).** 영상·정답·승자·점수판 중 어느 것도 채팅 피드나 입력창을 덮어서는 안 되며(SHALL NOT), 화면 전체를 덮는 오버레이로 표시해서도 안 된다(SHALL NOT). 영상은 **곡을 확인할 수 있는 정도의 축소 형태**로 표시한다 — 이 구간의 주된 페이로프는 계속 재생되는 정답 곡의 소리이며 영상은 시각적 확인 수단이다. 정답·승자·점수판은 라운드 정보 영역에 인라인으로 표시한다.

표시되는 영상은 **재생 제어 입력을 받아서는 안 된다(SHALL NOT).** 5초 남짓한 공개 구간에 참가자가 실수로 눌러 정답 곡을 멈추게 하는 사고를 막는다.

**정답이 공개될 때 채팅의 시청 위치가 어긋나서는 안 된다(SHALL NOT).** 공개 구간 진입으로 라운드 정보 영역이 커지면 채팅 메시지 영역이 그만큼 줄어드는데, 이때 바닥에 붙어 있던 위치가 유지되지 않으면 **정답 직후에 도착한 메시지가 화면 밖으로 밀려난다** — 채팅을 살리는 목적을 정확히 그 순간에 배반한다. 따라서 최신 메시지를 보고 있던 참가자는 공개 전후로 계속 최신 메시지를 봐야(SHALL) 한다. 반대로 **스스로 위로 스크롤해 과거 메시지를 보고 있던 참가자의 위치는 옮겨서는 안 된다(SHALL NOT).**

#### Scenario: 승자가 있으면 정답과 승자를 표시한다
- **WHEN** `type=ROUND_REVEALED`를 수신(`winnerId` 존재)
- **THEN** 정답(`title`)과 서버가 보낸 승자 닉네임(`winnerNickname`), 갱신된 점수판이 표시되어야 한다

#### Scenario: 승자가 공개 직후 퇴장해도 승자 이름이 유지된다
- **WHEN** `ROUND_REVEALED` 표시 중 승자가 방을 떠나 `type=LEFT`가 도착
- **THEN** 승자 이름이 계속 표시되어야 한다 (멤버 목록 변화가 이미 받은 공개 정보를 바꾸지 않는다)

#### Scenario: 타임아웃이면 정답과 시간 초과를 표시한다
- **WHEN** `type=ROUND_REVEALED`를 수신하고 `winnerId`가 null
- **THEN** 정답과 함께 아무도 맞히지 못했음이 표시되어야 한다

#### Scenario: 정답 공개 구간에 정답 곡이 들린다
- **WHEN** 라운드가 `REVEAL`로 전이됨
- **THEN** 정답 곡이 클립 시작 지점부터 다시 재생되어야 한다
- **AND** 아무도 맞히지 못해 클립이 이미 소진된 라운드에서도 들려야 한다
- **AND** 같은 구간에 다음 라운드 트랙의 선버퍼링이 함께 진행되어야 한다

#### Scenario: 정답 공개 구간에만 영상이 보인다
- **WHEN** 라운드가 `REVEAL`로 전이됨
- **THEN** 정답 곡의 영상이 정답·승자 정보와 함께 화면에 표시되어야 한다
- **AND** 선버퍼링 중인 다음 곡의 영상은 표시되지 않아야 한다

#### Scenario: OPEN 중에는 영상이 보이지 않는다
- **WHEN** 라운드가 `OPEN`이고 클립이 재생 중임
- **THEN** 영상이 화면에 표시되지 않아야 한다 (썸네일·제목이 정답을 노출하므로)

#### Scenario: 제스처 게이트가 떠 있는 동안에는 영상이 보이지 않는다
- **WHEN** 아직 arming되지 않아 제스처 게이트가 표시된 채로 라운드가 `REVEAL` 단계임
- **THEN** 정답 곡의 영상이 표시되지 않아야 한다
- **AND** 게이트를 통과한 뒤에는 남은 공개 구간 동안 영상이 표시되어야 한다

#### Scenario: 정답 공개가 채팅을 덮지 않는다
- **WHEN** 라운드가 `REVEAL`로 전이되어 영상과 정답·승자·점수판이 표시됨
- **THEN** 화면 전체를 덮는 오버레이가 사용되지 않아야 한다
- **AND** 채팅 피드와 입력창이 어떤 표시 요소에도 가려지지 않아야 한다

#### Scenario: 영상을 눌러도 정답 곡이 멈추지 않는다
- **WHEN** 참가자가 공개 구간에 표시된 영상 위를 누름
- **THEN** 재생이 멈추거나 바뀌지 않아야 한다

#### Scenario: 정답이 공개돼도 채팅이 최신 메시지에 머문다
- **WHEN** 최신 메시지를 보고 있던 참가자의 화면에서 라운드가 `REVEAL`로 전이되어 채팅 메시지 영역이 줄어듦
- **THEN** 정답 직전·직후에 도착한 메시지가 계속 보여야 한다
- **AND** 다음 라운드가 열려 영역이 다시 늘어날 때도 최신 메시지가 보여야 한다

#### Scenario: 과거 메시지를 보던 참가자의 스크롤은 끌려가지 않는다
- **WHEN** 위로 스크롤해 지난 메시지를 읽던 참가자의 화면에서 라운드가 `REVEAL`로 전이됨
- **THEN** 그 참가자의 스크롤 위치가 바닥으로 강제 이동되지 않아야 한다

### Requirement: 게임 종료 시 마지막 점수로 최종 결과 화면을 보여준다

시스템은 `ENDED`를 받으면 게임 종료로 처리하고, 직전 `ROUND_REVEALED`가 전달한 마지막 점수판(sticky 보존)으로 **최종 결과(순위) 화면**을 표시해야(SHALL) 한다. `ENDED` 메시지에는 점수판이 실리지 않으므로 프론트가 마지막 `scores`를 유지해 사용한다. `ENDED`는 행위자 유무(방장 수동 종료 vs 서버 주도 자연 종료)와 무관하게 게임 종료로 처리한다. 종료 후 방 상태는 `ACTIVE`로 복귀한다.

이 sticky 점수판은 **자기완결적이어야(SHALL) 한다** — 순위·닉네임·점수를 그리는 데 필요한 정보를 점수판 바깥(현재 멤버 목록 등)에서 찾지 않는다. 결과 화면은 게임이 끝난 시점의 기록이므로, **그 이후의 입·퇴장으로 표시 내용이 달라져서는 안 된다(SHALL NOT).**

#### Scenario: 게임이 끝나면 최종 순위가 표시된다
- **WHEN** `type=ENDED`를 수신
- **THEN** 마지막 `ROUND_REVEALED`의 점수판으로 순위(닉네임·점수)와 우승자 하이라이트가 표시되어야 한다
- **AND** 방 상태가 `ACTIVE`로 복귀해 로비로 돌아갈 수 있어야 한다

#### Scenario: 결과 화면이 뜬 뒤 퇴장한 참가자도 이름으로 표시된다
- **WHEN** 최종 결과 화면 표시 중 다른 참가자가 방을 떠나 `type=LEFT`가 도착
- **THEN** 그 참가자의 순위·닉네임·점수가 변하지 않고 그대로 표시되어야 한다
- **AND** 닉네임이 `(퇴장)` 같은 대체 문구로 바뀌지 않아야 한다

#### Scenario: 서버 주도 종료도 행위자 없이 결과를 보여준다
- **WHEN** 라운드 엔진이 서버 주도로 종료해 행위자(`playerId`/`nickname`) 없는 `ENDED`가 도착
- **THEN** 행위자 유무와 무관하게 최종 결과 화면이 표시되어야 한다

### Requirement: 재접속·새로고침 시 라운드 스냅샷으로 화면을 복원한다

시스템은 `PLAYING` 중 새로고침하거나 재접속하면 `GET /rooms/{roomId}` 응답의 `round` 스냅샷으로 현재 라운드 화면을 복원해야(SHALL) 한다. `OPEN`이면 정답 없이 클립·카운트다운·점수판을 복원하고, `REVEAL`/`ENDED`면 정답을 포함해 복원한다. 늦게 도착한 스냅샷이 더 진행된 라이브 상태를 되돌리지 않도록 `roundSeq` 단조 증가를 보장한다.

`OPEN` 단계를 복원할 때는 **포기 현황과 본인의 포기 여부도 함께 복원해야(SHALL) 한다.** 포기는 라운드 경계에서만 해제되는 상태이므로, 복원하지 않으면 재접속한 참가자만 자기 포기 상태를 잃어 컨트롤이 초기 상태로 보인다. 그 상태에서 다시 조작하면 실제로는 **포기가 취소되어** 화면과 반대로 동작한다.

#### Scenario: OPEN 중 재접속은 정답 없이 복원된다
- **WHEN** `OPEN` 라운드 진행 중 새로고침해 `round.phase=OPEN` 스냅샷을 받음
- **THEN** 클립·남은 시간·점수판이 복원되고 정답(`title`)은 표시되지 않아야 한다

#### Scenario: REVEAL 중 재접속은 정답까지 복원된다
- **WHEN** 재접속 시 `round.phase=REVEAL` 스냅샷(`title` 포함)을 받음
- **THEN** 정답·승자·점수판이 공개 상태로 복원되어야 한다

#### Scenario: 포기한 뒤 새로고침해도 포기 상태가 유지된다
- **WHEN** `OPEN` 라운드에서 포기한 참가자가 새로고침해 스냅샷을 받음
- **THEN** 포기 컨트롤이 포기 상태로 표시되어야 한다
- **AND** 포기 인원수와 필요 인원수가 함께 복원되어야 한다

### Requirement: 오디오 자동재생을 위해 사용자 제스처 게이트를 제공한다

시스템은 `PLAYING` 진입 시 오디오 자동재생이 브라우저 정책에 막히지 않도록 **1회 사용자 제스처 게이트**(예: "게임 참여 / 소리 켜기")를 제공해야(SHALL) 한다. 게이트 클릭으로 플레이어를 arming한 뒤에는 이후 라운드가 조용히 자동재생된다. 재접속으로 `PLAYING`을 복원할 때도 동일하게 게이트를 거친다. 음소거 자동재생은 노래 맞히기에 부적합하므로 사용하지 않는다.

단, arming 이후에도 브라우저가 자동재생을 차단할 수 있다. 플레이어가 **자동재생 차단을 통지하면**(IFrame API `onAutoplayBlocked`) arming이 소실된 것으로 보고, 요구사항 "클립이 재생되지 않으면 감지해 사용자에게 알린다"에 따라 제스처를 다시 유도한다.

#### Scenario: PLAYING 진입 시 제스처 게이트가 뜬다
- **WHEN** 참가자 화면이 `PLAYING`으로 전이되고 아직 arming되지 않음
- **THEN** 오디오 재생을 위한 1회 제스처 게이트가 표시되어야 한다

#### Scenario: 게이트를 통과하면 이후 라운드가 자동재생된다
- **WHEN** 사용자가 제스처 게이트를 클릭해 arming
- **THEN** 현재 및 이후 `ROUND_STARTED`의 클립이 추가 제스처 없이 자동재생되어야 한다

### Requirement: 클립이 재생되지 않으면 감지해 사용자에게 알린다

시스템은 arming된 상태에서 클립 재생을 시도했는데 재생이 시작되지 않으면 이를 **감지해 재생 불가를 화면에 알려야(SHALL)** 한다. 일부 YouTube 트랙은 임베드 플레이어에서 재생이 거부되며(콘텐츠 경고·임베드 차단 등) 이때 `onError`가 발생하지 않을 수 있으므로, 오류 이벤트만으로 판정하지 않고 **재생 개시 여부를 관찰**해 판정한다.

판정 규칙은 다음과 같다. 재생 시도 후 **3초** 안에 재생 개시(`PLAYING`)도 버퍼링 진입(`BUFFERING`)도 관찰되지 않으면 재생 불가로 판정한다. 오류 이벤트가 오면 3초를 기다리지 않고 즉시 판정한다. **버퍼링 진입은 플레이어 생존 신호**이므로 관찰되면 판정을 해제한다 — 느린 네트워크를 재생 불가로 오판하지 않기 위함이다. 3초는 최소 클립 예산(`clipLen × repeatCount + 2s`)이 약 17초임을 전제로, 안내를 보여줄 시간을 남기면서 버퍼링 신호가 도달하기에 충분한 값으로 정했다.

안내는 사용자가 자신의 오디오 설정을 의심하지 않도록 **"이 곡이 재생되지 않는다"는 사실을 명시**해야 하며, 브라우저 자동재생 정책에 막힌 경우(제스처 게이트로 해결 가능)와 **구분되는 안내**를 제공해야 한다.

재생 실패는 라운드 진행에 영향을 주지 않는다 — 라운드의 권위는 서버이므로 프론트는 재생 실패를 이유로 라운드를 종료·스킵하지 않고 서버의 `ROUND_REVEALED`를 그대로 기다린다.

#### Scenario: 재생이 시작되지 않으면 재생 불가를 알린다
- **WHEN** arming된 상태에서 클립 재생을 시도했으나 재생 개시도 버퍼링 진입도 관찰되지 않은 채 3초가 경과
- **THEN** 해당 곡을 재생할 수 없다는 안내가 표시되어야 한다
- **AND** 안내는 사용자의 오디오 설정 문제가 아님이 드러나야 한다

#### Scenario: 오류 이벤트가 오면 기다리지 않고 즉시 알린다
- **WHEN** 플레이어가 재생 불가를 나타내는 오류 이벤트를 발생시킴
- **THEN** 3초를 기다리지 않고 즉시 재생 불가 안내가 표시되어야 한다

#### Scenario: 버퍼링에 진입한 느린 재생은 재생 불가로 판정하지 않는다
- **WHEN** 클립이 버퍼링에 진입했으나 네트워크가 느려 3초 안에 재생이 시작되지 않음
- **THEN** 재생 불가 안내가 표시되지 않아야 한다
- **AND** 재생이 시작되면 정상적으로 클립이 들려야 한다

#### Scenario: 자동재생 정책 차단은 재생 불가와 구분한다
- **WHEN** 플레이어가 자동재생 차단을 통지(`onAutoplayBlocked`)
- **THEN** 재생 불가 안내가 아니라 소리 켜기를 다시 유도하는 안내가 표시되어야 한다

#### Scenario: 재생에 실패해도 라운드는 서버 권위로 계속된다
- **WHEN** 클립 재생에 실패한 채로 라운드가 진행 중
- **THEN** 카운트다운과 추측 채팅은 그대로 동작해야 한다
- **AND** 프론트가 라운드를 스스로 종료·스킵하지 않고 서버의 `ROUND_REVEALED`로 정답이 공개되어야 한다

### Requirement: 오디오 플레이어 초기화는 게임이 시작되기 전에 끝나야 한다

오디오 플레이어의 초기화 비용(아이프레임 생성·플레이어 부트스트랩)은 **어느 라운드도 부담해서는 안 된다(SHALL NOT)**. 이 비용은 어떤 곡을 재생할지 몰라도 치를 수 있으므로, 시스템(프론트)은 방에 입장한 시점 — 즉 게임이 시작되기 전 — 에 플레이어를 준비해야(SHALL) 한다. 플레이어 인스턴스는 방 세션 동안 유지되며 라운드마다 다시 만들어져서는 안 된다(SHALL NOT).

첫 라운드가 특별히 느려서는 안 된다는 것이 이 요구사항의 요지다. 첫 라운드 앞에는 정답을 노출하지 않고 트랙을 미리 받을 수 있는 구간이 없어 로드·버퍼링은 회수할 수 없지만, 부트스트랩은 트랙과 무관하므로 회수할 수 있다.

플레이어 인스턴스를 라운드 간에 유지하므로, 라운드 경계에서 초기화되어야 할 재생 상태는 명시적으로 초기화되어야(SHALL) 한다 — 반복 재생 카운터와 재생 가능 여부 판정은 라운드가 바뀔 때마다 새로 서야 한다.

> 영상 로드·버퍼링 구간은 본 요구사항이 아니라 아래 "클라이언트는 다음 라운드 트랙을 정답 공개 구간 동안 미리 버퍼링한다"가 다룬다.

#### Scenario: 게임 시작 전에 플레이어가 준비된다
- **WHEN** 멤버가 방에 입장해 아직 게임이 시작되지 않음
- **THEN** 오디오 플레이어가 이미 생성되어 재생 준비를 마쳐야 한다
- **AND** 이 시점에는 어떤 곡도 적재되어 있지 않아야 한다 (첫 라운드 정답이 노출되면 안 된다)

#### Scenario: 첫 라운드도 부트스트랩 비용을 부담하지 않는다
- **WHEN** `ROUND_STARTED`로 첫 라운드가 열림
- **THEN** 아이프레임 생성·플레이어 부트스트랩이 이 구간에서 발생하지 않아야 한다
- **AND** `ROUND_STARTED` 수신부터 재생 개시까지의 지연이 영상 로드·버퍼링 시간에 그쳐야 한다

#### Scenario: 라운드가 바뀌어도 플레이어를 다시 만들지 않는다
- **WHEN** 라운드가 전환되어 새 트랙으로 교체됨
- **THEN** 기존 플레이어 인스턴스에 곡만 교체되어야 하며 아이프레임이 다시 생성되어서는 안 된다

#### Scenario: 라운드가 바뀌면 반복 카운터가 초기화된다
- **WHEN** `repeatCount`만큼 재생을 마친 라운드에 이어 다음 라운드가 열림
- **THEN** 새 트랙이 `repeatCount`회 온전히 반복되어야 한다 (이전 라운드의 소진 카운트가 이월되지 않는다)

#### Scenario: 라운드가 바뀌면 재생 불가 판정이 새로 선다
- **WHEN** 이전 라운드에서 재생 불가(`unplayable`)로 판정된 뒤 다음 라운드가 열림
- **THEN** 새 트랙에 대해 재생 불가 판정이 처음부터 다시 수행되어야 한다
- **AND** 이전 라운드의 판정 결과가 새 라운드의 안내 UI에 남아 있지 않아야 한다

### Requirement: 클라이언트는 다음 라운드 트랙을 정답 공개 구간 동안 미리 버퍼링한다

클라이언트는 다음 라운드의 재생 참조를 받으면 — `ROUND_REVEALED` 이벤트로든 `REVEAL` 단계의 재접속 스냅샷으로든 — 정답 공개 구간 동안 그 트랙의 버퍼링을 시작해야(SHALL) 한다. 이로써 다음 라운드가 열릴 때 영상 로드·버퍼링이 이미 완료되어 있어야 한다.

선버퍼링된 트랙은 해당 라운드가 열리기 전까지 **소리를 내서는 안 된다(SHALL NOT)**. 정답 공개 구간에 다음 곡이 들리면 그 자체로 정답이 유출된다. 이 구간에는 정답 곡이 함께 재생되므로(위 `ROUND_REVEALED` 요구사항) 두 소리가 섞이지 않도록 선버퍼링 쪽은 반드시 음소거되어야 한다.

선버퍼링이 유발하는 플레이어 상태 전이는 **현재 라운드의 반복 재생 카운터와 재생 불가 판정에 영향을 주어서는 안 된다(SHALL NOT)**. 기존 요구사항이 버퍼링 진입을 "플레이어 생존 신호"로 삼아 재생 불가 판정을 해제하도록 규정하고 있어, 선버퍼링이 만든 전이를 구분하지 않으면 다음 라운드의 판정이 관찰도 하기 전에 해제되거나 반복 카운터가 잘못 소진된다.

> 재생 참조를 서버가 어느 시점에 어떤 형태로 내려보내는지(그리고 마지막 라운드에서 비어 있어야 한다는 경계 조건)는 서버 계약이므로 `room-game-session`의 요구사항이 다룬다.

#### Scenario: 다음 트랙을 받으면 즉시 버퍼링을 시작한다
- **WHEN** 클라이언트가 `ROUND_REVEALED` 또는 `REVEAL` 단계 스냅샷으로 다음 라운드의 재생 참조를 받음
- **THEN** 해당 트랙의 버퍼링을 즉시 시작해야 한다
- **AND** 버퍼링 중 소리가 나지 않아야 한다

#### Scenario: 선버퍼링 상태 전이는 현재 라운드의 판정을 건드리지 않는다
- **WHEN** 선버퍼링으로 플레이어에 `BUFFERING`·`PLAYING` 등의 상태 전이가 발생함
- **THEN** 현재 라운드의 반복 재생 카운터가 증가하지 않아야 한다
- **AND** 다음 라운드의 재생 불가 판정이 그 전이만으로 해제되지 않아야 한다

#### Scenario: 다음 트랙이 없으면 선버퍼링하지 않는다
- **WHEN** 마지막 라운드의 `ROUND_REVEALED`를 받아 다음 재생 참조가 비어 있음
- **THEN** 선버퍼링을 시도하지 않아야 하며 오류 없이 게임 종료로 진행되어야 한다

#### Scenario: 선버퍼링된 라운드는 로드 지연 없이 재생을 시작한다
- **WHEN** 선버퍼링을 마친 트랙의 라운드가 `ROUND_STARTED`로 열림
- **THEN** `ROUND_STARTED` 수신부터 재생 개시까지의 지연이 **500ms 이내**여야 한다

> 500ms는 기준선 1821ms에서 로드·버퍼링 1363ms가 선버퍼링으로 제거되고 부트스트랩 458ms도 플레이어 재사용으로 사라진다는 계산에 근거한 잠정치다. 태스크 6.2에서 실측이 갱신되면 위 요구사항의 70% 임계와 함께 재검토한다.

### Requirement: 채팅 피드의 비용은 세션 길이에 비례해 자라지 않는다

시스템(프론트)은 채팅 피드가 방 세션 동안 수신한 메시지 수에 비례해 **입력 지연이나 메모리가 무한히 자라지 않도록** 해야(SHALL) 한다. 게임 중 채팅은 정답 추측 채널이라 다른 화면보다 훨씬 빠르게 쌓이므로, 피드의 비용이 세션 길이에 묶이면 게임이 길어질수록 정답 입력 자체가 느려진다.

이를 위해 다음을 만족해야(SHALL) 한다:

- 채팅 피드는 **최근 N개**의 메시지만 유지한다(현재 N = 300). 상한을 넘으면 가장 오래된 메시지부터 제거한다. 시스템 메시지(입장·퇴장·시작·종료)도 같은 피드의 항목이므로 상한에 함께 포함된다
- 입력창에 글자를 입력하는 동작의 처리 시간은 피드에 있는 메시지 수와 **무관해야(SHALL)** 한다. 입력은 입력 영역 안에서만 처리되어야 하며, 피드·라운드 정보·오디오 플레이어의 표시를 갱신하는 작업을 유발해서는 안 된다(SHALL NOT)
- 새 메시지가 도착할 때의 처리 비용은 **세션 동안 수신한 총 메시지 수와 무관하게 일정한 상한 안에** 머물러야(SHALL) 한다. 피드가 상한에 도달한 뒤에도 메시지가 더 쌓인다고 처리 시간이 늘어나서는 안 된다

상한 N은 화면에 보이는 양(약 15~20개)을 충분히 넘어 몇 라운드 전의 대화를 되짚어 볼 수 있게 하되, DOM·메모리 상한이 눈에 띄지 않는 크기로 정한다. 값을 조정하면 이 요구사항의 현재 값도 함께 갱신한다.

기존의 바닥 추종 동작 — 새 메시지가 오면 바닥에 붙어 있던 참가자를 따라 내리고, 위로 스크롤해 과거를 보던 참가자는 끌어내리지 않는다 — 은 상한 절단이 일어난 뒤에도 그대로 유지되어야(SHALL) 한다. 절단으로 뷰포트 위쪽의 콘텐츠가 사라질 때 읽고 있던 위치는 **항목 하나 높이 이내**로만 이동해야 하며, 어느 브라우저에서도 절단이 바닥으로 끌어내리는 결과가 되어서는 안 된다(SHALL NOT). 위치 보정을 브라우저에 맡길지 직접 할지는 수단의 문제이므로 여기서 정하지 않는다.

> 이 요구사항은 관찰 가능한 결과만 규정한다. 메모이제이션·항목 식별자·스크롤 보정 수단은 `design.md`가 정한다.

#### Scenario: 상한을 넘으면 가장 오래된 메시지가 제거된다
- **WHEN** 피드에 N개의 메시지가 있고 새 `CHAT` 이벤트를 수신
- **THEN** 가장 오래된 메시지 하나가 피드에서 사라지고 새 메시지가 끝에 추가되어야 한다
- **AND** 피드의 메시지 수가 N개로 유지되어야 한다

#### Scenario: 입력 처리 시간이 메시지 수와 무관하다
- **WHEN** 피드가 상한까지 찬 상태에서 참가자가 입력창에 글자를 입력함(전송 전)
- **THEN** 키 입력 처리 시간이 피드가 비어 있을 때와 다르지 않아야 한다
- **AND** 피드·라운드 정보·오디오 플레이어의 표시가 갱신되지 않아야 한다

#### Scenario: 새 메시지 처리 비용이 세션 길이에 비례해 자라지 않는다
- **WHEN** 피드가 상한에 도달한 뒤 수천 개의 메시지가 더 오간 상태에서 새 `CHAT` 이벤트를 수신
- **THEN** 새 메시지를 표시하기까지의 처리 시간이 상한에 처음 도달했을 때와 다르지 않아야 한다
- **AND** 체감되는 지연이 없어야 한다

#### Scenario: 절단 뒤에도 바닥 추종이 유지된다
- **WHEN** 피드가 상한에 도달해 앞쪽 메시지가 제거되는 중에 바닥을 보고 있던 참가자에게 새 메시지가 도착
- **THEN** 스크롤이 계속 바닥에 붙어 최신 메시지가 보여야 한다

#### Scenario: 절단이 위로 스크롤한 참가자를 끌어내리지 않는다 (Chrome·Firefox)
- **WHEN** Chrome 또는 Firefox에서 참가자가 위로 스크롤해 과거 메시지를 읽는 중에 피드 앞쪽이 절단됨
- **THEN** 스크롤이 바닥으로 끌려가지 않아야 한다
- **AND** 읽고 있던 메시지가 화면에서 뛰지 않아야 한다

#### Scenario: 절단이 위로 스크롤한 참가자를 끌어내리지 않는다 (Safari)
- **WHEN** Safari에서 참가자가 위로 스크롤해 과거 메시지를 읽는 중에 피드 앞쪽이 절단됨
- **THEN** 스크롤이 바닥으로 끌려가지 않아야 한다
- **AND** 읽고 있던 위치의 이동이 제거된 항목 하나의 높이를 넘지 않아야 한다

#### Scenario: 세션 길이와 무관하게 입력 지연이 일정하다
- **WHEN** 같은 방에서 수천 개의 채팅이 오간 뒤 참가자가 입력창에 글자를 입력
- **THEN** 키 입력 처리 시간이 방에 처음 입장했을 때와 다르지 않아야 한다
