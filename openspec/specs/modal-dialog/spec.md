# modal-dialog Specification

## Purpose

프론트엔드 공용 모달(대화 상자)의 동작 계약을 정의한다. 핵심 원칙은 **열림 상태의 단일 소유권**이다 — 모달은 열림 여부를 스스로 결정하거나 저장하지 않고, 부모가 내려준 `isOpen`만을 따르며 사용자의 닫기 의도는 `onClose()` 신호로만 전달한다. 닫기 거부는 `onClose`를 무력화하는 방식이 아니라 `dismissible` 정책으로 선언한다. 이로써 "부모의 `isOpen`은 `true`인데 모달은 사라져 다시 열 수 없는" 상태 굳음이 구조적으로 발생하지 않는다.

여기에 더해 대화 상자로서 갖춰야 할 접근성 계약을 포함한다: ESC 닫기 요청, 포커스 트랩과 트리거로의 포커스 복원, 결정론적 초기 포커스(파괴적 동작이 기본 포커스가 되지 않을 것), 배경 스크롤 잠금, 표시 제목과 일치하는 접근 가능한 이름, 그리고 모달이 열려 있어도 가려지지 않는 전역 알림. 퇴장 애니메이션 종료 신호가 오지 않는 환경(`prefers-reduced-motion` 포함)에서도 모달이 화면에 남지 않아야 한다는 요구를 함께 규정한다.

또한 모달이 닫힌 뒤 완료되는 비동기 작업(방 입장 연결·방 생성 등)의 늦게 도착한 결과가 사용자를 원치 않는 화면으로 이동시키지 않도록 하는 계약을 다룬다.

## Requirements

### Requirement: 열림 상태는 부모의 `isOpen`만이 소유한다

모달은 열림 여부를 **자체적으로 판단하거나 저장하지 않아야(SHALL NOT)** 하며, 화면에 보이는지 여부는 오직 부모가 전달한 `isOpen` prop을 따라야(SHALL) 한다. 배경 클릭·ESC 등 사용자의 닫기 동작은 `onClose()` 호출로만 전달되고, 모달은 그 즉시 스스로 열림 상태를 바꾸지 않아야(SHALL NOT) 한다. 모달 내부의 상태는 퇴장 애니메이션 동안 DOM 유지를 위한 파생 상태로만 쓰이며, 열림 여부를 결정하지 않는다.

닫기 요청을 받아들일지는 모달의 **`dismissible` 정책**(기본값: 허용)이 결정해야(SHALL) 한다. `dismissible`이 꺼진 모달은 사용자의 배경 클릭·ESC를 닫기 요청으로 부모에게 올리지 않아야(SHALL NOT) 한다(플랫폼이 대화 상자를 실제로 닫아버린 경우의 상태 동기화는 예외 — "닫힌 뒤 같은 트리거로 다시 열 수 있다" 요구사항을 따른다). 반대로 `onClose()`가 호출된 경우 부모는 이를 **무조건 이행해 `isOpen`을 `false`로 내려야(SHALL)** 한다 — `onClose`를 무시하거나 조건부로 거부하는 방식으로 닫기를 막아서는 안 된다(SHALL NOT).

#### Scenario: 닫기 요청을 받으면 부모가 이행해 닫힌다
- **WHEN** `dismissible`이 켜진 모달에서 사용자가 배경을 클릭
- **THEN** `onClose()`가 호출되어야 한다
- **AND** 부모가 이에 반응해 `isOpen`을 `false`로 내리면 모달이 퇴장 애니메이션 후 사라져야 한다

#### Scenario: `dismissible`이 꺼진 모달은 배경 클릭으로 닫히지 않는다
- **WHEN** `dismissible`이 꺼진 모달에서 사용자가 배경을 클릭
- **THEN** `onClose()`가 호출되지 않고 모달이 화면에 그대로 남아 있어야 한다
- **AND** `isOpen`과 실제 표시 상태가 어긋나지 않아야 한다

### Requirement: 닫힌 뒤 같은 트리거로 다시 열 수 있다

모달이 어떤 경로로 닫히든(배경 클릭·ESC·내부 버튼·**브라우저가 강제로 닫는 경우**) 부모의 `isOpen`은 실제 표시 상태와 일치해야(SHALL) 하며, 사용자는 처음과 동일한 트리거로 모달을 다시 열 수 있어야(SHALL) 한다. 부모가 `isOpen`을 `true`로 유지한 채 모달만 사라져 재오픈이 불가능해지는 상태에 도달해서는 안 된다(SHALL NOT).

이를 위해 모달은 **대화 상자가 실제로 닫혔다는 플랫폼 신호를 구독해**, 자신이 시작하지 않은 닫힘에 대해서도 `onClose()`를 호출해 부모 상태를 동기화해야(SHALL) 한다. 정상 경로(부모가 `isOpen`을 내려 시작된 닫힘)에서 `onClose()`가 중복 호출되어서는 안 된다(SHALL NOT).

#### Scenario: 곡 추가 레이어를 배경 클릭으로 닫은 뒤 '+'로 다시 연다
- **WHEN** 새 플레이리스트 화면에서 '+'로 곡 추가 레이어를 열고 레이어 바깥을 클릭해 닫음
- **THEN** 레이어가 닫히고 `isOpenEditTrack`이 `false`가 되어야 한다
- **AND** 다시 '+'를 누르면 곡 추가 레이어가 정상적으로 열려야 한다

#### Scenario: 연결 중 닫기 요청이 억제되어도 상태가 어긋나지 않는다
- **WHEN** 비밀번호 입력 모달에서 입장 연결이 진행 중(`isLoading`)일 때 사용자가 배경을 클릭
- **THEN** 닫기 요청이 억제되어 모달이 화면에 그대로 유지되어야 한다
- **AND** 연결이 실패로 끝난 뒤 사용자가 다시 닫으면 정상적으로 닫히고, 이후 다른 비밀번호 방을 눌렀을 때 모달이 다시 열려야 한다

#### Scenario: 브라우저가 강제로 닫아도 다시 열 수 있다
- **WHEN** `dismissible`이 꺼진 모달에서 브라우저가 닫기 억제를 무시하고 대화 상자를 닫음(예: 중간 조작 없이 ESC를 연속으로 두 번 누름)
- **THEN** 모달이 그 닫힘을 감지해 `onClose()`를 호출하고 부모의 `isOpen`이 `false`가 되어야 한다
- **AND** 같은 트리거를 다시 누르면 모달이 정상적으로 다시 열려야 한다

### Requirement: 진행 중인 작업을 가진 모달이 닫히면 늦게 도착한 결과가 사용자를 이동시키지 않는다

모달이 닫힌 **뒤에 완료될 수 있는 비동기 작업**(방 입장 연결, 방 생성 등)을 진행 중인 모달은, 그 작업이 도는 동안 닫기 요청을 억제해야(SHALL) 한다. 다만 그 억제는 최선 노력이므로(ESC 관련 요구사항 참조), 억제가 뚫려 모달이 닫힌 경우에도 **모달이 닫힌 뒤 도착한 결과가 화면 이동 등 후속 동작을 실행해서는 안 된다(SHALL NOT).** 사용자가 빠져나온 화면으로 뒤늦게 끌려 들어가서는 안 된다(SHALL NOT).

되돌릴 수 있는 부수 효과는 정리되어야(SHALL) 하고, 되돌릴 수 없는 서버 부수 효과는 남되 사용자가 그 결과에 스스로 접근할 수 있어야(SHALL) 한다 — 자동으로 이어지는 동작만 억제되고, 이미 일어난 서버 변경이 사용자에게 감춰져서는 안 된다(SHALL NOT).

#### Scenario: 강제로 닫힌 뒤 늦게 도착한 연결 성공이 방으로 이동시키지 않는다
- **WHEN** 비밀번호 모달이 연결 대기 중 강제로 닫힌 뒤, 그 요청의 연결 성공 결과가 뒤늦게 도착
- **THEN** 그 결과는 무시되어야 하며 사용자가 방 화면으로 이동해서는 안 된다
- **AND** 만들어진 연결은 정리되어 누수되지 않아야 한다

#### Scenario: 방 생성 중 모달을 닫으면 자동 입장하지 않고 방이 목록에 나타난다
- **WHEN** 방 만들기 모달에서 '만들기'를 누른 뒤 생성이 끝나기 전에 모달이 닫혔고(ESC 등), 그 뒤 생성 성공 결과가 도착
- **THEN** 사용자가 그 방으로 자동 입장해서는 안 된다
- **AND** 이미 만들어진 방은 방 목록에 나타나 사용자가 직접 선택해 입장할 수 있어야 한다

#### Scenario: 생성이 진행되는 동안 배경 클릭은 억제된다
- **WHEN** 방 만들기 모달에서 생성 요청이 진행 중일 때 사용자가 배경을 클릭
- **THEN** 닫기 요청이 억제되어 모달이 그대로 유지되어야 한다

### Requirement: 닫히면 어떤 환경에서도 화면에 남지 않는다

모달은 `isOpen`이 `false`로 바뀌면 퇴장 애니메이션을 재생한 뒤 DOM에서 제거되어야(SHALL) 한다. 애니메이션이 끝났음을 알리는 신호가 오지 않는 환경에서도 모달이 화면에 남아 있어서는 안 된다(SHALL NOT). 동작 축소 설정(`prefers-reduced-motion: reduce`)에서도 모달은 즉시 사라지고 이후 같은 트리거로 다시 열 수 있어야(SHALL) 한다.

제거 시점을 어떤 신호로 판정할지는 관측되지 않는 구현 결정이며 `design.md` Decision 3이 다룬다.

#### Scenario: 동작 축소 설정에서도 모달이 정상적으로 닫힌다
- **WHEN** 사용자 환경이 `prefers-reduced-motion: reduce`이고 모달을 닫음
- **THEN** 모달이 즉시(애니메이션 없이) 사라져야 한다
- **AND** 이후 같은 트리거로 다시 열 수 있어야 한다

#### Scenario: 애니메이션 종료 이벤트가 오지 않아도 언마운트된다
- **WHEN** 어떤 이유로 퇴장 애니메이션 종료 이벤트가 발생하지 않음
- **THEN** 모달이 DOM에서 제거되어 화면에 남지 않아야 한다
- **AND** 이후 같은 트리거로 다시 열 수 있어야 한다

### Requirement: 다시 열면 이전 내용이 남지 않는다

모달이 닫힌 뒤 다시 열렸을 때 직전에 열렸을 때의 입력 값이나 선택 상태가 남아 있어서는 안 된다(SHALL NOT). **모달이 보장하는 범위는 자신의 children 서브트리**다 — 모달은 닫힘이 완료되면 children을 언마운트하고 다시 열릴 때 새로 마운트해야(SHALL) 한다.

모달은 자신보다 **위에** 보관된 상태는 리셋할 수 없으므로, 폼 상태를 모달 바깥(부모 컴포넌트)에 두는 소비자는 재오픈 시 그 상태를 **스스로 초기화해야(SHALL)** 한다. 어느 쪽 경로를 쓰든 사용자가 보는 결과는 같아야 한다.

퇴장 애니메이션이 진행되는 동안 부모가 `isOpen`을 다시 `true`로 올리는 경우에도 모달은 모순 없이 등장 상태로 되돌아가야(SHALL) 하며, 그때에도 위 결과는 동일해야(SHALL) 한다. 다만 모달이 열려 있는 동안(퇴장 애니메이션 중 포함) 배경은 비활성화되므로, 이 경로는 사용자가 배경 트리거를 눌러 만들어 낼 수 있는 조작이 아니다.

#### Scenario: 곡 편집 레이어를 닫고 다른 곡을 클릭하면 그 곡이 표시된다
- **WHEN** 곡 A를 편집하던 레이어를 ESC·배경 클릭으로 닫아 사라진 뒤 곡 목록에서 곡 B를 클릭
- **THEN** 레이어가 다시 열리고 곡 B의 정보(URL·제목·재생 구간·반복 횟수·추가 정답)가 표시되어야 한다
- **AND** 곡 A의 입력 값이 남아 있지 않아야 한다

#### Scenario: 폼 상태를 모달 바깥에 두는 소비자도 재오픈 시 초기화된다
- **WHEN** 방 만들기 모달에 방 이름·플레이리스트를 입력하다 배경을 클릭해 닫고, 모달이 사라진 뒤 '방 만들기' 카드를 다시 클릭
- **THEN** 모달이 다시 열리고 방 이름·비밀번호·선택한 플레이리스트가 모두 초기 상태여야 한다

### Requirement: ESC 키로 닫기를 요청할 수 있다

모달이 열려 있는 동안 ESC 키 입력은 배경 클릭과 동일한 **닫기 요청**으로 처리되어야(SHALL) 한다. `dismissible`이 켜져 있으면 `onClose()`가 호출되어 모달이 닫힌다.

`dismissible`이 꺼져 있을 때 ESC 억제는 **최선 노력(best effort)** 이다 — 플랫폼의 닫기 남용 방지 규칙 때문에 억제가 통하지 않고 대화 상자가 강제로 닫히는 경우가 있다. 그 경우에도 `isOpen`과 실제 표시 상태가 어긋나서는 안 되며(SHALL NOT), 모달은 닫힘을 감지해 부모 상태를 동기화해야(SHALL) 한다.

#### Scenario: ESC로 곡 추가 레이어가 닫힌다
- **WHEN** 곡 추가 레이어가 열린 상태에서 ESC를 누름
- **THEN** 레이어가 닫히고 '+'로 다시 열 수 있어야 한다

#### Scenario: `dismissible`이 꺼진 모달은 통상적인 ESC로는 닫히지 않는다
- **WHEN** 입장 연결 중(`isLoading`)인 비밀번호 모달에서 사용자가 (직전 조작으로 활성화가 살아 있는 상태에서) ESC를 한 번 누름
- **THEN** 모달이 닫히지 않고 그대로 유지되어야 한다
- **AND** 그럼에도 플랫폼이 강제로 닫는 경우에는 부모의 `isOpen`이 함께 `false`가 되어 재오픈이 가능해야 한다

### Requirement: 모달이 열린 동안 포커스가 모달 안에 머무르고 닫으면 트리거로 돌아온다

모달이 열리면 포커스는 모달 내부로 이동해야(SHALL) 하며, Tab·Shift+Tab 이동은 모달 내부 요소들 사이에서만 순환해야(SHALL) 한다. 모달 뒤의 배경 요소는 포커스를 받을 수 없어야(SHALL NOT) 한다. 모달이 닫히면 포커스는 모달을 연 트리거 요소로 돌아가야(SHALL) 한다.

모달이 열릴 때의 **초기 포커스 위치는 결정론적으로 지정되어야(SHALL)** 한다. 브라우저 기본 규칙(트리 순서상 첫 포커스 가능 요소)에 맡기면 파괴적인 동작 버튼이나 교차 출처 iframe이 잡힐 수 있으므로, 초기 포커스 대상은 모달을 여는 쪽이 명시하고 대화 상자가 실제로 열린 뒤에 적용되어야(SHALL) 한다. 확인/취소처럼 파괴적 동작이 포함된 모달의 초기 포커스는 **비파괴 선택지**에 놓여야(SHALL) 하며, 되돌릴 수 없는 동작이 기본 포커스가 되어서는 안 된다(SHALL NOT).

포커스 복원은 트리거가 포커스 가능할 때만 성립하므로, **곡 추가 '+' 버튼·'방 만들기' 카드·방 카드**는 포커스 가능한 요소여야(SHALL) 하며 키보드만으로 활성화할 수 있어야(SHALL) 한다. 곡 목록 행과 데스크톱 네비게이션의 뒤로가기 항목은 이번 범위 밖이며(각각 중첩 인터랙티브 요소, `<Link>` 중첩 문제), 그 트리거로 연 모달은 닫을 때 포커스가 문서 본문으로 복원되는 한계가 남는다.

#### Scenario: 곡 추가 레이어를 키보드만으로 열고 닫는다
- **WHEN** Tab으로 곡 목록의 '+'에 도달해 Enter로 누름
- **THEN** 곡 추가 레이어가 열리고 포커스가 레이어 내부(YouTube URL 입력)로 이동해야 한다
- **AND** ESC로 닫으면 포커스가 다시 '+'로 돌아와야 한다

#### Scenario: 비밀번호 방에 키보드만으로 입장을 시도한다
- **WHEN** 방 목록에서 Tab으로 비밀번호가 걸린 방 카드에 도달해 Enter로 누름
- **THEN** 비밀번호 입력 모달이 열리고 포커스가 비밀번호 입력으로 이동해야 한다
- **AND** ESC로 닫으면 포커스가 다시 그 방 카드로 돌아와야 한다

#### Scenario: 되돌릴 수 없는 동작이 기본 포커스가 되지 않는다
- **WHEN** 플레이리스트를 편집하다 뒤로가기 확인 모달을 염(편집 내용을 버리는 '확인'과 '취소'가 있음)
- **THEN** 초기 포커스가 '취소'에 있어야 하며, 열자마자 Enter를 눌러도 편집 내용이 버려지지 않아야 한다

#### Scenario: 미리보기 iframe이 있어도 초기 포커스가 입력으로 간다
- **WHEN** URL이 이미 입력된 기존 곡을 클릭해 곡 편집 레이어를 염(YouTube 미리보기 iframe이 렌더된 상태)
- **THEN** 초기 포커스가 iframe이 아니라 YouTube URL 입력에 있어야 하며, 그 상태에서 ESC로 레이어를 닫을 수 있어야 한다

#### Scenario: Tab이 모달 밖으로 새지 않는다
- **WHEN** 모달이 열린 상태에서 Tab을 반복해서 누름
- **THEN** 포커스가 모달 내부 요소들만 순환해야 하며 배경의 입력창·버튼·네비게이션에 도달하지 않아야 한다

### Requirement: 모달이 열린 동안 배경이 스크롤되지 않는다

모달이 열려 있는 동안 배경 페이지는 스크롤되지 않아야(SHALL) 하며, 모달이 닫히면 원래 스크롤 동작이 복원되어야(SHALL) 한다. 모달이 여럿 동시에 열릴 수 있으므로 스크롤 잠금은 참조 카운트로 관리되어, 하나가 닫혀도 다른 모달이 열려 있으면 잠금이 유지되어야(SHALL) 한다.

#### Scenario: 모달이 열리면 배경이 고정된다
- **WHEN** 모달이 열린 상태에서 마우스 휠·터치로 스크롤을 시도
- **THEN** 배경 페이지가 스크롤되지 않아야 한다
- **AND** 모달 내용이 화면보다 길면 모달 내부는 스크롤되어야 한다

#### Scenario: 모달을 닫으면 배경 스크롤이 복원된다
- **WHEN** 열려 있던 모달을 모두 닫음
- **THEN** 배경 페이지 스크롤이 원래대로 동작해야 한다

### Requirement: 모달에 접근 가능한 이름이 있다

모달은 대화 상자로 노출되어야(SHALL) 하며, 화면에 표시되는 제목과 **동일한** 텍스트를 접근 가능한 이름으로 가져야(SHALL) 한다. 제목이 조건에 따라 달라지는 모달(예: `곡 추가` / `곡 편집`)에서도 표시 제목과 접근 이름이 어긋나서는 안 된다(SHALL NOT). 이를 위해 접근 이름은 제목 텍스트를 문자열로 중복 전달하는 방식이 아니라, 실제로 렌더된 제목 요소를 참조하는 방식으로 연결되어야(SHALL) 한다.

#### Scenario: 곡 편집 시 접근 이름이 표시 제목을 따라간다
- **WHEN** 기존 곡을 클릭해 레이어를 염(표시 제목이 `곡 편집`)
- **THEN** 대화 상자의 접근 가능한 이름도 `곡 편집`이어야 한다

#### Scenario: 모든 모달이 제목을 헤딩으로 노출한다
- **WHEN** 곡 추가·편집, 뒤로가기 확인, 방 만들기, 비밀번호 입력 모달을 각각 염
- **THEN** 각 모달의 제목이 헤딩 요소로 렌더되고 대화 상자의 접근 가능한 이름으로 연결되어야 한다

### Requirement: 모달이 열려 있어도 전역 알림이 보인다

모달이 열려 있는 동안 발생한 전역 알림(토스트)은 모달과 그 배경 위에 **가려지지 않고 표시되어야(SHALL)** 한다. 모달을 연 채 알림만으로 결과를 전달하는 경로(예: 방 생성 실패)에서 사용자가 그 결과를 알아차리지 못하는 상태가 되어서는 안 된다(SHALL NOT).

알림 표시 영역이 모달의 조작을 가로막아서는 안 된다(SHALL NOT) — 알림이 떠 있어도 모달 안의 입력·버튼을 그대로 사용할 수 있어야(SHALL) 한다. 모달이 열려 있지 않은 일반 화면에서 알림의 위치와 동작은 종전과 같아야(SHALL) 한다.

#### Scenario: 방 생성 실패 알림이 모달 위에 보인다
- **WHEN** 방 만들기 모달에서 '만들기'를 눌렀고 생성이 실패함(모달은 열린 채로 유지된다)
- **THEN** 실패 알림이 모달과 배경 위에 선명하게 표시되어야 한다
- **AND** 사용자는 알림을 본 뒤에도 모달 안에서 입력을 고쳐 다시 시도할 수 있어야 한다

#### Scenario: 모달을 연 뒤에 뜬 알림도 가려지지 않는다
- **WHEN** 알림이 표시되기 전에 모달을 먼저 열고, 그 뒤 알림이 발생
- **THEN** 알림이 모달 위에 표시되어야 한다(모달을 여는 순서와 무관하게 성립해야 한다)
